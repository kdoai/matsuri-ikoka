# ログインと保存の仕様

旅程・しおりの共有・相談の途中の状態を Firestore に残し、ログインした利用者が自分の旅を残して、あとで開き、消せるようにします。判断の理由は [ADR 0005](../adr/0005-login-and-storage.md) にあります。

## ログイン

| 項目           | 決まり                                                                                                                                                                  |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 方法           | Firebase Authentication の、メールアドレスとパスワード、または Google（ポップアップ）。どちらでも ID トークンの確かめ方と持ち主の決まりは同じ                           |
| いつ要るか     | 旅を残す・あとで開く・一覧する・共有する・消すとき。相談はログインなしで始められる。ログインして使った相談は、その人に結びつく（[利用者ごとの分離](#利用者ごとの分離)） |
| 利用者の決め方 | 画面が `Authorization: Bearer <ID トークン>` で送る Firebase の ID トークンを、サーバーが Admin SDK で確かめる。画面が送る利用者の ID は使わない                        |
| 画面の設定     | `GET /api/auth/config` が Firebase の公開の設定（`apiKey`・`authDomain`・`projectId`）を返す。用意していなければ `{ "enabled": false }` で、ログインのボタンを出さない  |
| 部品の読み込み | Firebase の部品は、ログインを用意しているときだけ読み込む。`{ "enabled": false }` のときは読み込まない                                                                  |

### 登録・ログイン・再設定

| 操作                         | 動き                                                                                                                                                                                                                                      |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 登録                         | メールアドレスと8文字以上のパスワード。登録するとそのままログインする。下限は画面と Firebase のパスワードの決まり（`apply` で入れる）でそろえる。メールアドレスの確かめは必須にしない（手軽に試せるようにするため。上限は IP でも数える） |
| ログインの失敗               | 登録がないときもパスワードが違うときも「メールアドレスかパスワードが違います」と出す                                                                                                                                                      |
| 登録の失敗                   | 「登録できませんでした。登録したことがあれば、ログインするか、パスワードを再設定してください」と出し、登録があるとは言わない                                                                                                              |
| パスワードの再設定           | 登録があってもなくても同じ文を出す。メールが届くのは登録があるときだけ                                                                                                                                                                    |
| パスワードの変更             | ログイン中の人に、再設定と同じメールを送る                                                                                                                                                                                                |
| ログアウト・アカウントの削除 | 前の人の旅程と会話を画面に残さず、新しい相談を自動で始める                                                                                                                                                                                |

登録の失敗の文は有無を言わないようにしていますが、登録できたかどうかから、そのメールアドレスの有無は分かります。メールアドレスの有無を隠す設定は登録の応答を変えません。メールアドレスの確かめを先に求めれば隠せますが、手軽さを優先して求めません。

### 同じメールアドレスで別の方法を使ったとき

1つのメールアドレスに1つのアカウントとします（Firebase の既定）。方法をつなぐ画面は作りません。

| 先に使った方法                         | あとから使った方法            | 動き                                                                                                                                                                                                                        |
| -------------------------------------- | ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Google                                 | パスワードで登録              | 登録を断る（上の「登録の失敗」の文）                                                                                                                                                                                        |
| パスワード（メールの確認をしていない） | Google（`@gmail.com`）        | Google のログインが優先され、同じ利用者の ID のまま Google でログインする。前のパスワードは使えなくなる。残した旅はそのまま。先に他人がそのメールアドレスで登録していても、持ち主が Google で入れば他人のパスワードは消える |
| パスワード                             | Google（`@gmail.com` のほか） | 断り、「別の方法で登録されています」と出す。Google で本人と確かめたあとの文なので、有無を見せることにはならない                                                                                                             |

### 使いすぎの対策

- メールアドレスの有無を隠す設定（`emailPrivacyConfig.enableImprovedEmailPrivacy`）を `scripts/setup-firestore.sh apply` で入れる
- 登録の数は、Firebase の IP ごとの上限（既定）で抑える。一時的に下げたいときは Firebase のコンソールで変える
- 登録し直しても相談の上限を回避できないよう、1日の回数はログインしていても IP で数える（`DAILY_CHAT_LIMIT_PER_IP`）。同じ IP の人は枠を分け合う
- 1日の回数は Firestore（`dailyLimits`）にも残し、インスタンスが止まって起動し直しても、その日の数を読み戻す（[1日の回数の数え](operations.md#1日の回数の数え)）
- reCAPTCHA を有効にするときは、ページの CSP（`routes/web.ts`）に読み込み先を足す。いまの CSP のままでは読み込みが止まる
- 試した回数が多すぎるときは「しばらく待って」と出す（`auth/too-many-requests`）

### 消す前の確かめ直し

アカウントを消す前に、本人を確かめ直します。パスワードの人はパスワードを入れ、Google の人は確かめの窓を開きます。**サーバーに旅を消すよう頼む前に**確かめるので、確かめられなければ何も消えず、旅だけが消えてアカウントが残ることもありません。窓がブラウザに止められないよう、消すボタンを押した操作の中で開きます。

## お試し用のアカウント

アカウントを作らずに機能を試せるよう、同じメールアドレスとパスワードを何人かで使うアカウントを1つ用意できます。利用者の ID は決まった値（`TRIAL_ACCOUNT_UID`）で、この ID で見分けます。ID はサーバーが ID トークンから確かめるので、ほかの人は名乗れません。ほかの人の旅との分離は、ふつうの利用者と同じです。

| 操作                       | 動き                                                                                                                                                                                 |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 旅を残す・開く・1つ消す    | できる。残した旅は、同じアカウントを使うほかの人にも見えるので、画面でそう伝える                                                                                                     |
| パスワードの変更           | 画面に出さず、画面の通信の部品でも断る。サーバーの経路はないので、サーバーでは断らない                                                                                               |
| 旅とアカウントをすべて消す | 画面に出さず、画面の通信の部品でも断り、`DELETE /api/me/trips` は 403 で断る                                                                                                         |
| ログインの方法             | サーバーはパスワードでのログインのトークンだけを通す。Google などを結びつけても、それでは入れない                                                                                    |
| 初期の状態に戻す           | スクリプトの `reset`。残した旅・共有・ガイドのデータ・相談の途中の状態を消し、結びつけたものと名前・写真を外し、メールアドレスを戻し、ログインしている人を外す。パスワードは変えない |
| 回数と費用の上限           | IP ごとに数え、全体の枠はお試し用だけで別に持つ（`DAILY_TRIAL_CHAT_LIMIT`・`GUIDE_DAILY_COST_USD_TRIAL_TOTAL`）。メモリに持つので `reset` では戻らず、日付が変わるか再起動で戻る     |

ログインしている人を外すのに Admin SDK の `checkRevoked` は使いません（Auth を読む権限が要るので）。スクリプトが `accountState/trial` に時刻を書き、サーバーはお試し用のトークンのときだけそれを読んで、前のログインを断ります。読めないときも断ります。ふつうの利用者のトークンは署名と期限だけを確かめます。

Firebase には、特定のアカウントだけパスワードの変更と削除を止める設定がありません。ID トークンを持つ人が Firebase の API を直接呼ぶと、変更や削除ができてしまいます。そのときは `rotate-password` でパスワードを作り直すか、消されたら `create` で同じ ID のまま作り直します（残した旅はそのまま読めます）。消されたあとに同じメールアドレスを取られたら、`create` は案内を出して止まるので、別のメールアドレスを渡すか、そのアカウントをコンソールで消します。

```bash
FIREBASE_PROJECT_ID=<プロジェクト ID> TRIAL_ACCOUNT_EMAIL=<メールアドレス> pnpm --filter @matsuri-ikoka/server trial:account create
```

- コマンドは `create`（作る）・`reset`（初期の状態に戻す）・`rotate-password`（パスワードを作り直す）
- パスワードは実行のときに乱数で作り、その端末の画面にだけ出す。ファイルとログには書かない。CI では動かない
- メールアドレスは受信できなくても動くが、`@gmail.com` は使わない（Google でログインされるとパスワードが使えなくなる）

## 残すもの

読み書きは接客サーバーだけが行います。ブラウザから Firestore への読み書きは、セキュリティルール（[`firestore.rules`](../../firestore.rules)）ですべて断ります。

| 文書                                    | 中身                                                                                                                                                    | 消える時刻（`expiresAt`）                                |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| `itineraries/{旅程の ID}`               | 一覧の見出し（名前・初日）、残した利用者の ID（`ownerUid`）、組んだ相談の利用者の ID（`consultOwnerUid`）、最新の版、作った時刻、最後に保存した時刻     | 残されていなければ最後の保存から30日。残した旅は消さない |
| `itineraries/{旅程の ID}/versions/{版}` | 旅程の JSON（版ごと、新しいものから20版まで）                                                                                                           | 旅程と同じ                                               |
| `shares/{共有の ID}`                    | 共有したときの版の旅程の JSON、旅程の ID、持ち主                                                                                                        | 作ってから30日                                           |
| `sessions/{相談の ID}`                  | 相談の途中の状態（条件・こだわり・候補・選んだ祭り・旅程の ID・段階、記録の再生の位置）、持ち主（`ownerUid`）                                           | 最後に使ってから6時間                                    |
| `dailyLimits/{枠}-{日}`                 | 1日の相談の回数の数え（枠は全体 `chat`・利用者と IP ごと `client`・お試し用 `trial`）。キーは IP と利用者の ID から作った仮名のキー（塩なしのハッシュ） | 最後に数えてから2日                                      |

- 旅程は形が変わっても保存の側を直さずに済むよう、丸ごと JSON の文字列で持つ。読むときに `ItinerarySchema` を通し、読めない古い版は「見つからない」として扱う
- 会話の文章と、Agent SDK の会話の記録は残さない
- TTL ポリシーで消えるまでには時間がかかる（多くは1日以内）ので、読むときにも期限を確かめる
- ID はどれも推測できない乱数（旅程は `trip-…`、共有は `sh-…`、相談は `s-…`）
- 旅の下のデータ（手帳・通知・提案・見回りの依頼）の形は [旅のガイドの仕様](guide.md#データの保存と消し方) にある。見回りの控えと実行の記録（`patrols`・`patrolRuns`・`patrolDeliveries`）は利用者の情報を持たない（[旅の見回り](operations.md#保存するもの)）

### 相談の続き

1. 相談を作ったとき、返事を作り終えたとき、こだわりを変えたときに、途中の状態を書く。旅程の書き込みが終わってから書くので、続きを受けたインスタンスは必ず旅程を読める
2. 発言が、相談を持っていないインスタンスに届いたら、途中の状態と旅程を Firestore から戻してから返事を作る
3. Agent SDK の会話の記録はインスタンスの `/tmp` にあるので、戻した相談では新しい会話を始め、相談の状態の要約から続ける
4. Firestore に書けなくても相談は止めず、そのインスタンスのメモリで続ける（ログに `storage_failed` を残す）

### 旅程の版

ツールが旅程を保存するたびに、その版を書きます。同じ旅程の書き込みは順に並べ、版が戻らないようにします。残した旅の新しい版は、持ち主の旅に入ります。

### しおりの共有

| URL                   | 読めるもの                 | 読める期間         |
| --------------------- | -------------------------- | ------------------ |
| `/shiori/{旅程の ID}` | 持ち主のない旅程の最新の版 | 最後の保存から30日 |
| `/shiori/{共有の ID}` | 共有を作ったときの版       | 作ってから30日     |

持ち主のある旅程は、旅程の ID では開けません（ない旅程と同じ 404）。開くのは、明示して作った共有の ID からです。

- 自分の旅の一覧の「しおりを開く」は、共有（作ってから30日）を作って開きます。残した旅は、最後の保存から30日を過ぎても、ここから開けます
- 店内のしおりの画面は、ログインしている人の旅程なら共有を作って開きます。ログインしていなければ、旅程の ID のまま開きます
- 共有を作るとき、同じ旅程・同じ内容で、残りが15日以上ある自分の共有があれば、新しく作らずにそれを返します。版が同じでも、開催の確かめ直しなどで内容が変われば別の共有になり、前の共有は前の内容のままです。残りが15日を切った共有は、受け取った人がすぐ開けなくならないよう使い回しません

## 利用者ごとの分離

相談には日程・出発地・同行者の情報が入ります。Firestore のセキュリティルールはサーバーの Admin SDK には効かないので、ほかの人のデータに触れないことは、サーバーのコードで守ります。判断の理由は [ADR 0011](../adr/0011-owner-isolation.md) にあります。

### 保存の口

| 決まり                       | 中身                                                                                                                                                                                                                                                                                                              |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 持ち主を決めてから呼ぶ       | 利用者の旅の読み書きは `storage.forOwner(持ち主)` が返す口にしかない。持ち主を渡さずに呼ぶ口はない                                                                                                                                                                                                                |
| 持ち主の ID は型で分ける     | `forOwner` が受け取るのは `OwnerId` だけで、ただの文字列は型の検査で落ちる。`OwnerId` を作れるのは、ID トークンを確かめた直後（`account/idToken.ts`）と、保存した相談の持ち主を戻すときだけ                                                                                                                       |
| 経路は保存の口を直接持たない | 経路が受け取るのは、宣言した決まり（[経路と認可の決まり](api.md#経路と認可の決まり)）に応じて絞られた口だけ。相談も、持ち主を確かめる入口（`Consultations`）からだけ受け取る                                                                                                                                      |
| 見回りは狭い別の口を使う     | 見回りは利用者の操作から呼ばれず、頼まれた旅を横断して読むので、`forOwner` ではなく `apps/server/src/patrol/store.ts` の口を使う。読めるのは頼まれた旅の依頼・旅程・通知だけで、旅程は持ち主が `watch` のパスの利用者と一致するときだけ読む。入口は内部の検証を通ったものだけで、利用者の ID トークンでは届かない |
| 文書の ID を確かめる         | 外から届いた ID に `/` などが入っていると別の文書を指せるので、読み書きの前に確かめ、ないものとして扱う                                                                                                                                                                                                           |

### 相談の持ち主

| 相談                     | 持ち主                                                                                                                       | 続けられる人                                           |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| ログインせずに使っている | なし                                                                                                                         | 推測できない相談の ID を知っている人（いままでどおり） |
| ログインして始めた       | その人                                                                                                                       | その人だけ。ほかの人とログインなしの人には 404         |
| 途中でログインして使った | はじめてログインして相談を開いた人（発言・こだわり・検索・旅を残すのほか、ガイドの状態を読むなど、読み取りだけの経路も含む） | その人だけ。ほかの人とログインなしの人には 404         |

- 持ち主は、相談の持ち主の経路（[経路と認可の決まり](api.md#経路と認可の決まり)）のどれかで、ログインした人が相談を開いたときに決まる。中身を変えない読み取りだけの経路でも決まる
- 持ち主は一度決まったら変わらない。保存の口でも、持ち主のない書き込みでは消えず、別の持ち主の書き込みでも変わらない
- 相談を保存の口から戻すときに旅程を読めなければ（消した・ほかの人が残した・前の形）、その旅程を相談から外し、聞き取りか候補の段階から旅程のない相談として続ける
- ログアウトすると、ログインして使った相談は続けられない。画面は新しい相談を自動で始める
- ない相談とほかの人の相談は、同じ応答で断り、あるかどうかを見せない

### 旅程の持ち主と読める人

| 旅程                     | だれのものか                | 旅程の ID で読める人 | 自分の旅の一覧 | 消える時刻         |
| ------------------------ | --------------------------- | -------------------- | -------------- | ------------------ |
| ログインせずに組んだ     | だれのものでもない          | ID を知っている人    | 出ない         | 最後の保存から30日 |
| ログインした相談で組んだ | その人（`consultOwnerUid`） | その人だけ           | 出ない         | 最後の保存から30日 |
| 「この旅を残す」で残した | その人（`ownerUid`）        | その人だけ           | 出る           | 消さない           |

- 共有の ID（`sh-…`）からは、持ち主が明示して作った版を、期限までだれでも読める
- ログインせずに組んだ旅程の相談に途中でログインすると、その次に保存した版から、その人の旅程になる。前に渡した旅程の ID の URL は、そのときから開けなくなる
- 旅を消すと、版と共有と、旅の下のデータ（ガイドの手帳・通知・提案・見回りの依頼）もいっしょに消える

### 新しいデータの置き場

旅と利用者に結びつく新しい種類のデータは、持ち主を含むパス（`users/{利用者の ID}/trips/{旅の ID}/…`）に置きます。パスは `ownerTripPath(持ち主, 旅, …)` で作ります。いまの `itineraries`・`shares`・`sessions` は移しません。

### ログと会話の記録

| 対象                   | 決まり                                                                                                                                                                                 |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ログ                   | 発言の本文・出発地などの位置・自由記述・ID トークン・合言葉を残さない。例外の文には入力が入ることがあるので、種類と場所だけを残す（`errorForLog`）。失敗の経路も含めてテストで確かめる |
| Agent SDK の会話の記録 | `resume` に渡すのは、その相談が受け取ったセッション ID だけ。画面からは指定できない（余分な項目は 400）。保存の口にも残さないので、別のインスタンスに移った相談は新しい会話を始める    |

## API

ログインが要る API（決まりは「ログインした持ち主」）は、ID トークンがない・確かめられないと 401（`unauthorized`）、ログインを用意していないと 404 で断ります。応答には `Cache-Control: private, no-store` を付けます。型は `packages/schema` の `account.ts` にあります。

| メソッド | パス                               | 本文                                       | 返すもの                                                                                                                      |
| -------- | ---------------------------------- | ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| GET      | `/api/auth/config`                 | —                                          | `AuthConfigSchema`（ログインは要らない）                                                                                      |
| GET      | `/api/trips`                       | —                                          | `TripListResponseSchema`（新しく保存した順）                                                                                  |
| POST     | `/api/trips`                       | `SaveTripRequestSchema`（`{ sessionId }`） | 201 `TripSummarySchema`。旅程がなければ 409、相談や旅程がほかの人のものなら 404                                               |
| GET      | `/api/trips/:id`                   | —                                          | `TripResponseSchema`（最新の版と、残っている版の一覧）                                                                        |
| GET      | `/api/trips/:id/versions/:version` | —                                          | `TripResponseSchema`（その版）                                                                                                |
| POST     | `/api/trips/:id/share`             | —                                          | 201 `ShareResponseSchema`（しおりのパスと期限）。同じ内容の共有があれば、それを返す                                           |
| DELETE   | `/api/trips/:id`                   | —                                          | 204。すべての版と共有もいっしょに消す                                                                                         |
| DELETE   | `/api/me/trips`                    | —                                          | `{ "deleted": 残した旅の件数 }`。自分の旅程（残す前のものも）と共有と相談の途中の状態をすべて消す。お試し用のアカウントは 403 |

- 旅を残すときは、旅程の ID ではなく相談の ID で指す。しおりの URL を受け取っただけの人が、他人の旅程を自分のものにできないようにするため
- 自分の旅でなければ、あるかどうかも見せず 404 にする
- ログインした相談で組んだ、残す前の旅程も、`GET /api/trips/:id`・`POST /api/trips/:id/share`・`DELETE /api/trips/:id` で扱える（一覧には出ない）
- 旅を消すと、手元の写しと相談の中のガイドのデータを捨て、次の発言かこだわりの変更の前に相談から旅程を外す。消した旅を次の発言で作り直さない。画面で開いている旅を消したときは、新しい相談を始める
- 返事の途中に消しても戻らない。先に流している返事を止め、消した相談と旅への保存を断ってから消す。別のインスタンスの返事は止められない（いまは最大1インスタンス）
- `/api/me/trips` が成功したあとにアカウントを消せなければ、画面は「ログインの記録を消せなかった」と出して新しい相談を始める。もう一度消せる

## 消す手段

| 消すもの                   | 方法                                                                                                                                                                                  |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 旅を1つ                    | 自分の旅の一覧の「消す」（`DELETE /api/trips/:id`）。版と共有と、ガイドの手帳・通知・提案・見回りの依頼もいっしょに消える                                                             |
| 旅とログインの記録をすべて | 一覧の「旅とログインの記録をすべて消す」。本人を確かめ直し、`DELETE /api/me/trips` のあと、画面が Firebase のアカウントを消してログアウトする。残す前の旅程と相談の途中の状態も消える |
| 残さなかった旅程と相談     | 何もしなくても、旅程は最後の保存から30日、相談の途中の状態は6時間で消える                                                                                                             |

## 手元で動かす

Firestore と Auth のエミュレーター（Firebase CLI と Java が要る）で動かせます。設定は [`firebase.json`](../../firebase.json) にあります。プロジェクト ID を `demo-` で始めると、エミュレーターの外には出ません。

```bash
firebase emulators:start --only firestore,auth --project demo-matsuri-ikoka
```

接客サーバーには、次の環境変数を、リポジトリのルートの `.env` に書くか、シェルで渡します（`pnpm dev` はルートの `.env` があれば読みます）。

```bash
MATSURI_STORAGE=firestore
FIREBASE_PROJECT_ID=demo-matsuri-ikoka
FIREBASE_WEB_API_KEY=demo-api-key
FIREBASE_AUTH_DOMAIN=demo-matsuri-ikoka.firebaseapp.com
FIRESTORE_EMULATOR_HOST=127.0.0.1:8085
FIREBASE_AUTH_EMULATOR_HOST=127.0.0.1:9099
```

- 何も渡さなければ、保存先はメモリで、ログインは出ない（いままでどおり）
- `FIRESTORE_EMULATOR_HOST` を付けて `pnpm test` を走らせると、Firestore の実装でも保存の口のテスト（`apps/server/src/storage/contract.ts`）を回し、ブラウザからの読み書きがセキュリティルールで断られることも確かめる（`apps/server/src/storage/firestoreRules.test.ts`）

CI にはエミュレーターがないので、Firestore の実装やセキュリティルールを変えたら、手元で次の手順で確かめます。

```bash
firebase emulators:exec --only firestore --project demo-matsuri-ikoka "pnpm exec vitest run apps/server/src/storage"
```

ログインの流れは、本物の Firebase の部品を Auth のエミュレーターにつないで確かめます（CI では偽物の部品で確かめます）。

```bash
firebase emulators:exec --only auth --project demo-matsuri-ikoka "pnpm exec vitest run apps/web/src/account"
```

CI では、ルールの書かれた内容（すべてを断る決まりが1つだけあること）と、メモリの実装での保存の口のテストを確かめます。

## Google Cloud の設定

[`scripts/setup-firestore.sh`](../../scripts/setup-firestore.sh) で入れて確かめます（`check` で確かめ、`apply` で入れる）。値は環境変数で渡し、リポジトリには書きません。

| 項目               | 内容                                                                                                                                                                                                                             |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| API                | Firestore、Identity Toolkit、Security Token、Firebase、Firebase Rules                                                                                                                                                            |
| データベース       | Firestore の `(default)`。ネイティブモード、`asia-northeast1`、削除の保護つき                                                                                                                                                    |
| TTL ポリシー       | コレクショングループ `itineraries`・`versions`・`shares`・`sessions`・`notices`・`proposals`・`guideUsage`・`dailyLimits`・`patrolRuns`・`patrolDeliveries` の `expiresAt`                                                       |
| 索引               | コレクショングループ `watch` の `status`（コレクショングループの範囲）。見回りが、頼まれた旅を探すのに使う。`dailyLimits` の `counts` は索引から外す（キーが IP の数だけ増え、探すのに使わない）                                 |
| セキュリティルール | [`firestore.rules`](../../firestore.rules)（ブラウザからはすべて断る）を `firebase deploy --only firestore:rules` で入れる                                                                                                       |
| 権限               | Cloud Run の実行用のサービスアカウントに `roles/datastore.user` だけを足す。ID トークンの確認には権限が要らない（`checkRevoked` は権限が要るので使わない）                                                                       |
| ログイン           | プロジェクトに Firebase を足し、Authentication で Google のログインを有効にする。メールアドレスとパスワードのログインと、メールアドレスの有無を隠す設定を `apply` で有効にする。ログインを許すドメインに Cloud Run の URL を足す |
| Cloud Run          | 環境変数 `MATSURI_STORAGE=firestore`・`FIREBASE_PROJECT_ID`・`FIREBASE_WEB_API_KEY`・`FIREBASE_AUTH_DOMAIN`                                                                                                                      |

`FIREBASE_WEB_API_KEY` と `FIREBASE_AUTH_DOMAIN` は、Firebase のウェブアプリの公開の設定の値です。秘密の値ではありませんが、リポジトリやワークフローには書かず、Cloud Run のサービスの設定に置きます。`apply` で入れれば、デプロイ（`--update-env-vars`）はほかの環境変数を消さないので残ります。足りなければ `check` が「不足」と出します。

`apply` は Cloud Run の新しい版を作ります。デプロイのあとは通信が最新の版に向いているので、そのまま新しい版に切り替わります。前の版に戻した（`rollback.yml`）あとは通信が版に固定されているので、`gcloud run services update-traffic` の `--to-latest` か次のデプロイまで、新しい版に通信が向きません。環境変数を入れる前の版に戻すと、ログインも出なくなります。
