# 運用と安全の仕様

祭りの知識が新しく保たれること、コードとデータが必ず検査を通ってから公開されること、外からの攻撃や使いすぎに備えることの3つを決めます。

## 祭りのデータの更新

> いま動くのは、既存の祭りの開催情報を確かめる週に1回の調査です。新しい祭りの発見と追加は、手元の Claude Code で調査のスキルを使って調べ、PR で取り込みます。データの検証（`pnpm validate:data`）は CI で走り、確かめた日が古い情報を警告します。
>
> エージェント・環境・定期実行の定義は [`managed-agents/`](../../managed-agents/README.md)、調べる祭りの選び方と台帳は [`scripts/research-schedule.ts`](../../scripts/research-schedule.ts)、報告の検査は [`scripts/research-report.ts`](../../scripts/research-report.ts)、準備と回収は [`scripts/research-run.ts`](../../scripts/research-run.ts)、差分の分け方と PR の本文の作り方は [`scripts/festival-refresh.ts`](../../scripts/festival-refresh.ts) にあります。`pnpm refresh:targets` で、今週調べる祭りと理由を一覧にできます（調査はしない空実行）。`--issues` に `gh issue list --json number,body,labels` の出力を渡すと、依頼の Issue も対象に加えます。判断の理由は [ADR 0009](../adr/0009-weekly-research-on-managed-agents.md) にあります。

### 調べる祭りの選び方

週に1回、開催日の近い順に並べて、次の順で選びます（[`scripts/research-schedule.ts`](../../scripts/research-schedule.ts)）。同じ祭りを何度も調べず、開催が迫った祭りの確認を後回しにしないためです。

1. 次の祭りを除きます
   - 掲載停止（`optOut: true`）の祭り、確認待ちの PR にある祭り
   - いまの開催回が確定している（発表済みで、公式か複数の情報源で確認できた）か、中止と決まっている祭り。開催が終わると次の開催回が対象になります
   - 待ちのフラグが立っている祭り（下の表）
2. 開催まで14日以内で未調査の祭りと、待ちが明けた祭りを、件数の上限なしで全部選びます
3. 20件に満たなければ、まだ調べていない祭りを近い順に足します。足すのは120日先までです
4. 対象がなければ、その週は調べません

待ちのフラグは最低の件数より優先します。掲載・訂正・掲載停止の依頼や、接客中に見つかった公式情報との食い違いがある祭りは、確定済みや待ちのフラグがあっても選び、先頭に並べます。

いまの開催回は、これから先でいちばん近い開催回です。データに先の開催回がなければ、前回の1年後を仮の日付にします。

#### 調査の台帳

調べた結果は、祭りのデータとは別の `data/research-ledger.json` に残します。コードだけが書き込み、モデルの出力をそのまま入れません。CI で形を検証します。

| 結果                            | 次に調べるとき                                                                     |
| ------------------------------- | ---------------------------------------------------------------------------------- |
| 見つからなかった（`not_found`） | 残りの日数より短い次の節目（開催の30日前・14日前・7日前）。7日前より後なら調べない |
| 見つかった（`found`）           | PR がマージされれば確定。却下されたら次の節目                                      |
| 調べ切れなかった（`failed`）    | 翌週。2回続けて失敗したら次の節目                                                  |

たとえば21日前に見つからなければ次は14日前、60日前なら30日前です。実行は週に1回なので、「14日前」の調査は開催の8〜14日前のどこかになります。

確定しないまま開催が終わると、その回の記録を `officialNotFound` に移します。この記録は調べる祭りの選び方には使わず、今後の情報の集め方を考える材料にします。

#### 依頼の Issue から祭りを決める

依頼の Issue は、テンプレートが付けるラベル（`data-correction`・`listing-request`・`opt-out`）で種類を決め、「祭りの名前」の欄から祭りの ID を決めます。欄にデータにある ID がそのまま書かれていればそれを使い、なければ祭りの名前（日本語・英語。全角と半角、大文字と小文字の違いはならす）で探します。決まるのはデータにある ID だけで、本文のほかの文字は使いません。欄がない、どの祭りにも当たらない、複数の祭りに当たる依頼は、対象に入れずに一覧に出し、人が確かめます（まだデータにない祭りの掲載の依頼も、ここに出ます）。


差分は、調べ直す前と後の祭りを比べ、下の「マージのルール」の種類に分けます。表にない変更（見込みから発表への確定、作法・周辺の場所・そのほかの中身の変更、掲載停止の変更）は、人が確かめる側に入れます。出典は、付いている場所（開催回は日付、周辺の場所は ID、地元の味は名前）と URL で同じものかを見ます。

調べ直した結果は、PR の本文にまとめます（`refreshPullRequestBody`）。中止・延期を先頭に、人が確かめるもの、自動でよいものの順に、祭りごとの変更の種類と、変わった出典（追加・更新・消えた。URL・確度・確認した日）を書きます。変わらなかった祭りは数だけを書き、スキーマや検証に落ちて取り込まなかった祭りは理由とともに書きます。1件でも人が確かめるものか取り込まなかったものがあれば、PR 全体を人が確かめる側にします。祭りの名前や理由は調査で集めた信用しない文字列なので、Markdown・HTML の記号と `@` を打ち消し、1行にして書きます。

接客中の再確認で公式情報との食い違いが見つかると、次の調査でその祭りを優先します。使われるほど、データが正確になる仕組みです。

### 流れ

調査そのものは Claude Managed Agents の中で進めます。GitHub Actions（`update-festivals.yml`）はモデルを使わず、その前後の短い仕事だけを行います。

| いつ（日本時間）             | どこで                     | 何をするか                                                                                                         |
| ---------------------------- | -------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| 日曜 21:00                   | GitHub Actions（準備）     | 依頼の Issue を集め、調べる祭りをコードで選び、セッションが読むだけの Memory Store に調査リストを置く              |
| 月曜 6:00                    | Managed Agents（定期実行） | リードが調査員に祭りごとの調査を任せ、`found` の報告を確認役が見直し、採点役が基準で確かめる。報告をファイルに書く |
| 月曜 12:00・18:00、火曜 6:00 | GitHub Actions（回収）     | 終わったセッションの報告をコードで確かめ、変える祭りと台帳を PR にする。動いている途中なら次の回で確かめる         |

調査のチームは次のように分けます。

| 役                        | モデル           | 使える道具                 | 仕事                                                                   |
| ------------------------- | ---------------- | -------------------------- | ---------------------------------------------------------------------- |
| リード                    | Sonnet           | 読み取り、書き込み         | 調査リストを読み、仕事を任せ、報告を書く。4件以上なら並列に進める      |
| 調査員                    | Sonnet           | Web の検索と取得、読み取り | 1つの祭りを調べ、決まった形の JSON で報告する                          |
| 確認役                    | Sonnet           | ページの取得、読み取り     | `found` の報告の根拠のページを開いて確かめる                           |
| 採点役（Outcomes の機能） | リードと別の文脈 | 成果物の読み取り           | 報告がそろい、形が合っているかを基準で確かめ、足りなければやり直させる |

調査員と確認役には、調査のスキル（`.claude/skills/festival-research`）だけを渡します。`.claude/` のほかのスキル・エージェント・フックや `CLAUDE.md` は渡しません。

- 調査員は、主催者 → 市町村 → 観光協会 → 地元の報道 → SNS → 旅行サイトの順にたどり、検索の言葉を変えて調べます。`not_found` はたどった先を `tried` に書き、足りなければ採点役が差し戻します
- 公式でなくても、信頼度を評価して採用します。今回の日付が年つきで信頼できる情報源に出ていれば `announced`、主催者や自治体の決まり（「毎年11月8日」など）と合うだけなら `expected` です。決まりと、報道や観光サイトの年つきの日付が一致すれば、確定として扱います。報道や観光サイトが1つだけなら確度は `single` のままで、画面では未確認と出て、次の節目で調べ直します
- ページの取得（`web_fetch`）は、検索結果や開いたページに出た URL しか開けません。調査員は、分かっている出典（`knownSources`）を検索の手がかりにします
- ページの取得と書き込み（`write`）は `auto` にし、呼び出しごとにサーバーが判断します。確認待ちに答える人はいないので、止まった祭りは報告なしとして翌週に調べ直します。拒否や確認待ちの呼び出しは、開いたページとして数えません。止まった呼び出しの数は回収のログに出ます

ワークフローは2つのジョブに分けます。

| ジョブ     | 権限                                                                   | 仕事                                                                                                       |
| ---------- | ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 準備と回収 | リポジトリ・Issue・PR を読む、ID トークン（GitHub への書き込みはない） | 調査リストを置く。報告を確かめ、変える祭りのファイル・台帳・PR の本文を成果物にする                        |
| PR を開く  | ブランチの push、PR の作成、CI の承認（Anthropic のトークンはない）    | 成果物のファイルだけを `chore/refresh-festivals-<実行の番号>` にコミットし、PR を開き、PR の CI を承認する |

- 祭りの中身が変わるか、取り込まなかった報告がある PR には `status:manual` を付け、人が確かめてマージする。台帳だけが変わる PR は、CI が通れば自動でマージしてよい
- `GITHUB_TOKEN` で開いた PR の CI は承認待ちで止まるので、PR のジョブが承認する。ブランチにあるのはこのジョブが置いたファイルだけで、必須の検査になるのは PR に結びついた CI だけである
- 回収のあと、調査リストを空にする。準備が動かなかった週の定期実行は、空のリストを読んで何もせずに終わる
- 止めるときは、`MATSURI_REFRESH_ENABLED` を `true` 以外にして `setup` を実行する。定期実行が止まり、GitHub Actions の定期のきっかけも何もしなくなる

### 手で動かす

GitHub の Actions の画面で `update-festivals.yml` を main で起動し、行うことを選びます。

| 行うこと  | 内容                                                                                                                      |
| --------- | ------------------------------------------------------------------------------------------------------------------------- |
| `plan`    | `ant apply --dry-run` で、`managed-agents/` のファイルと API の資源の差分を見る                                           |
| `setup`   | `ant apply` で適用し、`MATSURI_REFRESH_ENABLED` に合わせて定期実行を動かすか止める。`claude-lock.json` の更新は PR で届く |
| `prepare` | 今週の調査リストを置く。`limit` で件数を絞れる                                                                            |
| `trigger` | 定期実行を待たずに1回起動する                                                                                             |
| `collect` | 終わったセッションの報告を回収する                                                                                        |

### 認証

API キーを置かず、Workload Identity Federation で、GitHub の ID トークンを短い Anthropic のトークン（10分）に換えます。連携のルールは次のすべてに一致するときだけトークンを出し、調査専用のワークスペース `matsuri-festival-research` の中だけで使えます。権限は `workspace:developer` で、サービスアカウントの役割は開発者です。

- リポジトリは `kdoai/matsuri-ikoka`（名前と数値の ID で照合）で、ブランチは main
- ワークフローは main の `update-festivals.yml` だけ。ほかのワークフローからは認証できない
- きっかけは `schedule` か `workflow_dispatch` だけ。フォークからの PR では動かない

ルールは Claude Console で作ります。ワークフローのファイル名を変えるときは、ルールも直します。

ワークフローは、次の GitHub Actions の変数（`vars`）を読みます。どれも秘密情報ではありません。

| 変数                                                                                                                  | 内容                                |
| --------------------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| `MATSURI_REFRESH_ENABLED`                                                                                             | `true` のときだけ定期の調査を動かす |
| `ANTHROPIC_FEDERATION_RULE_ID`・`ANTHROPIC_ORGANIZATION_ID`・`ANTHROPIC_SERVICE_ACCOUNT_ID`・`ANTHROPIC_WORKSPACE_ID` | Workload Identity Federation の設定 |

GitHub Actions に PR の作成を許す設定も要ります。モデル名と費用の上限は、変数ではなく `managed-agents/` の定義ファイルで管理します。

### 費用

1回の実行の目安は 20 米ドル以下です。定期実行の `budget` が上限で、届くとセッションが止まり、調べ残した祭りは翌週に調べ直します。件数の上限は設けず、調査の深さは保ったまま、次のように抑えます。

- 調査員の検索は12回、ページは15件までにする
- 確認役は `found` の報告だけを、根拠のページだけ見る
- 採点のやり直しは2回までにする
- 確定した開催回や待ちのフラグが立っている祭りを調べない

費用はモデルのトークン、検索（1,000回で10米ドル）、セッションの動いている時間（1時間で0.08米ドル）の合計です。回収のログに、実行ごとの費用を出します。

### 報告の検査

調査員は、祭りのデータ全体ではなく、決まった形の報告（`ResearchReportSchema`）を返します。変えられるのは任された開催回の日付・時刻・状態・雨天の扱い・備考・出典だけで、作法や掲載停止などのほかの項目は報告では変えられません。回収のコードが、次のどれかに当たる報告を取り込まず、理由を PR の本文に書きます。

- JSON として読めない、形が合わない、`pnpm validate:data` と同じ検証でエラーになる
- 調査リストにない祭りや、別の開催回の報告である
- 根拠のページを、セッションの中で実際に開いていない（すべてのスレッドの記録と照らす）
- ページを取り直すと、引用が本文にない
- 文字の中に URL・HTML・指示に見える文がある

PDF やスクリプトで描かれたページは機械で引用を照合できないので、PR の本文に書いて人が確かめます。

費用の上限に届くなどで報告のなかった祭りは「調べ切れなかった」として、翌週に調べ直します。実行のログには、件数と費用だけを出し、調べた語やページの中身は出しません。

### プロンプトインジェクションへの備え

祭りの公式サイトは前もって列挙できないので（出典のサイトは 648 あり、許可リストの上限は 64）、Web の許可リストは使いません。代わりに、ページに悪い指示があっても被害が出ない形にします。

- **読む役と書く役を分ける**：ページを読むエージェントは書き込めず、書くエージェントはページを読まない
- **盗めるものを置かない**：コマンドの実行はどのエージェントにも許さない。セッションに秘密の値・GitHub の権限・個人情報を置かない。調査リストは読み取り専用
- **報告の形を固定する**：決まった項目の値・出典の URL・短い引用だけを受け取り、変えてよい項目をコードで限る。報告にない時刻や備考は前の値を残し、その根拠として前の出典も残す
- **コードで確かめる**：上の「報告の検査」。モデルの判断に頼らない
- **人が確かめる**：祭りの中身が変わる PR は人がマージする。PR の本文はコードが作り、記号を打ち消す。1時間ごとの自動のマージは `status:manual` の PR を扱わない
- **権限と費用を絞る**：連携のルールを1つのワークフローと1つのワークスペースに限る。実行ごとに費用の上限を付ける

Memory Store に、調査員が書き込める学習の記憶は持たせません。悪い指示が翌週以降まで残るのを防ぐためです。

### マージのルール

すべてを人が確かめると更新が止まり、すべてを自動にすると誤りが入ります。そこで、変更の種類で分けます。自動のマージも、CI の検査がすべて通った場合に限ります。

| 変更の種類                         | マージ                           |
| ---------------------------------- | -------------------------------- |
| 確認した日の更新だけ（中身は同じ） | 自動                             |
| 出典の追加、確度が上がる           | 自動                             |
| 知名度の付け直し                   | 自動                             |
| 新しい祭りの追加                   | 人が確かめる                     |
| 開催日・時間・会場の変更           | 人が確かめる                     |
| 中止・延期                         | 人が確かめる（優先して知らせる） |
| 確度が下がる、出典が消える         | 人が確かめる                     |

### 祭りの側からの依頼

祭りを運営する方は、GitHub の Issue のテンプレート（祭りカードとしおりからリンクする）で、掲載・情報提供の依頼、訂正、掲載停止を頼めます。Issue は公開されるので、どのテンプレートにも、個人の連絡先を書かないよう注意書きを置きます。

- **掲載・情報提供の依頼**：寄せられた情報は「手がかり」として扱う。調査のスキルで公式の情報と照らし合わせてから載せ、確度のルールは変えない（依頼の内容だけでは `official` にも `corroborated` にもしない）。来る人に知ってほしい作法やしきたりは、公式の情報で確かめたうえで作法の項目に反映する
- **訂正の依頼**：次の直前の確認で優先して調べる
- **掲載停止の依頼**：データに `optOut: true` を付けてすぐに候補から外し、調査の対象からも除く

### 食い違いの記録

`verify_festival` が公式情報との食い違いを見つけると、サーバーは祭りの ID と内容を構造化ログ（`kind: "festival_discrepancy"`）に出します。直前の確認のジョブ（未実装）は、最初にこの記録を読んで調べる対象に加えます。動いているサーバーに、GitHub への書き込みの権限を持たせないためです。

## 旅の見回り

頼まれた旅について、祭りの中止・順延・時間の変更と宿の空きの変化を、裏で定期的に確かめます。週次の調査（祭りのデータの更新）とは目的も頻度も違うので、別の仕組みにしています。ガイドとしての動きは [旅のガイドの仕様](guide.md#見回り)、判断の理由は [ADR 0012](../adr/0012-trip-patrol.md)、コードは `apps/server/src/patrol/` と `apps/server/src/routes/patrol.ts`、見回り係の定義は [`managed-agents/`](../../managed-agents/README.md) にあります。

### 見回りの流れ

| 順  | どこで                     | 何をするか                                                                                                                                                            |
| --- | -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Cloud Scheduler            | 定期的に `POST /internal/patrol/start` を OIDC のトークンつきで呼ぶ                                                                                                   |
| 2   | サーバー（コード）         | 頼まれた旅から祭りと開催日を集める。同じ祭りと開催日は、いくつの旅で見張っていても1つにまとめる。掲載停止の祭りは対象にしない                                         |
| 3   | サーバー（コード）         | 公開のページを取得し、行に分けて前回と比べる。変わらなければ調べた時刻だけを残し、モデルを呼ばない                                                                    |
| 4   | サーバー（コード）         | 宿の空きは、モデルを使わず今の空室検索の処理で調べる                                                                                                                  |
| 5   | Managed Agents（見回り係） | 変わったページとコードで読めないページだけを、祭りごとにまとめて渡す。対象の URL は開始の発言に入れる。ページを読み、決まった形の JSON で報告する                     |
| 6   | サーバー（コード）         | Webhook の薄い通知を署名で確かめ、ID で重複を除き、結果を取りに行く。Webhook が届かなくても、次の定期の起動で古い実行を確かめる                                       |
| 7   | サーバー（検問）           | スキーマ・URL・出典を確かめ、前回の値と比べて変化の種類をコードで決める。確かな変化だけを、該当する旅の通知（`users/{uid}/trips/{旅の ID}/notices/{ID}`）の候補にする |

Cloud Run の CPU はリクエストの間だけ割り当てられるので、起動と結果の受け取りは、応答を返す前に終えます。起動は新しい対象に取りかかる時間を 180 秒までに区切り、残りは次の回に回します。

### 行の比べ方

- ページは本文の行だけを取り出し、全角と半角と空白の違いをならします。残すのは行のハッシュだけで、ページの文章をコピーしません
- 相対的な時刻（「3日前」「さっき」など）だけの変化は無視します。区切りに挟まれたものだけを消すので、「開催の3日前まで」のような決まりの数字が変われば更新として扱います。日付・時刻・数字の変化は更新です
- はじめて読めたページは、比べる元を残すだけで、モデルを呼びません
- 指示に見える行は、比べる対象にも、見回り係に渡す行にも、検問の根拠にも入れません
- 比べる元は、見回り係の結果を確かめてから新しくします。見回り係が失敗したら元のままなので、次の回に同じ変化を調べ直します

ページの取得は `checkPublicWebUrl` と名前の向き先の確認を、転送のたびに通します。`robots.txt` で断られたページは読みません。同じサイトは1秒以上空けて読みます。

| ページの結果                                     | 動き                                                        |
| ------------------------------------------------ | ----------------------------------------------------------- |
| 読めて、変わっていない                           | モデルを呼ばない                                            |
| 読めて、変わった                                 | 変わった行と URL を見回り係に渡す                           |
| 読めない（スクリプトで描く・PDF・機械を断る）    | 見回り係に任せる。同じページは1日に1回まで                  |
| 通信やサーバーの失敗                             | 間隔を空けて読み直す（空ける時間は失敗ごとに倍、上限は7日） |
| URL が公開の Web でない・`robots.txt` で断られた | 読まない。見回り係にも任せない                              |

### 検問

見回り係の報告は信用しない入力です。次を確かめ、通らないものは捨てて、分類だけを実行の記録とログに残します。

- 形：`PatrolReportSchema` に合う JSON で、依頼の `patrolId` と同じであること（`@matsuri-ikoka/agent-kit` で取り出す）
- 読んだページ：依頼にあり、セッションの中で実際に開いたページであること
- 値：変わったと言う日付・時刻、中止・延期の言葉が、コードで読み直した新しい行に書いてあること。「雨天の場合は中止」のような決まりの説明は、中止として扱いません。読み直しに使うのはコードの比較の結果なので、ページの指示で見回り係の報告が変わっても通りません
- 写した文：`dateText` がページにそのまま書いてあること。照合だけに使い、残しません

| 確かめられたこと                                                | 通知の候補                                              |
| --------------------------------------------------------------- | ------------------------------------------------------- |
| 公式のページか、2つのサイトの新しい行に、変更や中止が書いてある | 開催の変更（`schedule_change`）・中止（`cancellation`） |
| 公式でない1つのサイトだけに書いてある                           | 値を持たないお知らせ（`announcement`）                  |
| コードで読めないページで、変更や中止と報告された                | 値を持たないお知らせ（`announcement`）                  |
| 新しい行があるページで、お知らせの種類が報告された              | お知らせ（`announcement`）                              |
| 変わったと言う値が、読めるページの新しい行にない                | なし（捨てる）                                          |

同じ変化は同じ ID の通知になるので、同じ旅に2度届きません。1つの旅の通知は `MAX_NOTICES_PER_TRIP` 件までです。

### 二重起動と中断

祭りと開催日ごとの作業に実行権を持たせ、Firestore のトランザクションで取ります。作業中はページを読むごとに延ばし、5分で切れます。

| 場面                                 | 動き                                                                                |
| ------------------------------------ | ----------------------------------------------------------------------------------- |
| 同じ起動が2回届いた                  | 実行権を取れたほうだけが作業する。調べる時期でない対象は飛ばす                      |
| 作業が途中で止まった                 | 実行権が切れたら、次の起動が引き継ぐ                                                |
| 実行権を失った                       | 保存せず、その対象の作業をやめる                                                    |
| 見回り係の結果を待っている           | 同じ対象を調べ直さない。6時間届かなければ失敗として調べ直す                         |
| 同じ Webhook が2回届いた             | 配信の ID（`webhook-id`）で重複を除く。処理に失敗したら印を放し、再送で受け取り直す |
| Webhook と定期の起動が重なった       | 結果の受け取りも実行権で1つに絞る                                                   |
| 確認待ちで止まった呼び出し           | 確かめる人はいないので、サーバーが断る。読めなかったページは次の回に調べ直す        |
| 見回り係が失敗した・報告が崩れていた | 通知を作らず、比べる元を変えず、間隔を空けて調べ直す                                |

### 入口の決まり

`POST /internal/patrol/start` は `oidc`、`POST /internal/patrol/webhook` は `signature` の検証を通ったものだけを受け付けます（[内部の入口](api.md#内部の入口)）。確かめられなければ 401、検証の設定がなければその入口だけ 404 で、ハンドラーには届きません。設定がないから通す、という動きはしません。署名を確かめる前に、本文を処理せず、保存も取得もしません。

見回りの設定がなくても、サーバーは起動し、相談はそのまま動きます。`checkProductionConfig` の必須の項目には入れていません。

### 保存するもの

| 置き場                                      | 中身                                                                            | 消える時期                                        |
| ------------------------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------- |
| `users/{uid}/trips/{旅の ID}/watch/current` | 見回りの依頼。見回りは読むだけ                                                  | [旅のガイドの仕様](guide.md#データの保存と消し方) |
| `users/{uid}/trips/{旅の ID}/notices/{ID}`  | 通知。`expiresAt`（TTL）を足す                                                  | 旅を消すとき。旅の最終日から30日                  |
| `patrols/{祭りの ID}_{開催日}`              | 行のハッシュ・調べた時刻・実行権・検問を通った開催の日時                        | 見回る旅がなくなったとき                          |
| `patrolRuns/{見回りの ID}`                  | 実行の記録：調べた祭りと URL、セッションの ID、検問の結果の数、費用、失敗の分類 | 30日（TTL）                                       |
| `patrolDeliveries/{配信の ID}`              | Webhook の配信の受け取りの印                                                    | 7日（TTL）                                        |

`patrols` と `patrolRuns` に、利用者の情報とページの文章を置きません。実行の記録は、見回り係に渡した変わった行を残しません。

見回り中の旅は `watch` のコレクショングループを `status` で読むので、この項目のコレクショングループの索引が要ります。`notices`・`patrolRuns`・`patrolDeliveries` の `expiresAt` には TTL ポリシーが要ります。

### 見回りの権限

見回り係は、ページの取得の道具だけを持ちます。セッションに秘密の値・データベースの権限・利用者の情報を置きません。渡すのは祭りの公開の情報（ID・名前・開催日）と URL、変わった行だけで、型（`PatrolRequestSchema`）が決まった項目のほかを受け付けません。

サーバーは、見回り係の定義を置いたワークスペースの API キー（`PATROL_ANTHROPIC_API_KEY`）でセッションを作ります。接客の `ANTHROPIC_API_KEY` とは分け、見回りだけを止めたり鍵を回したりできるようにします。

### 見回りの費用

費用のほとんどは、変化があったときの見回り係です。次のように抑えます。

- 変わらないページではモデルを呼ばない
- 同じ祭りと開催日は、いくつの旅で見張っていても1回だけ調べる
- 1回の起動で調べる対象は `PATROL_MAX_TARGETS` まで（既定 20。超えた対象は次の回に回す）
- セッションごとに予算（`PATROL_SESSION_BUDGET_USD`、既定 2 米ドル、上限 10 米ドル）を付ける。届くとセッションが止まり、次の回に調べ直す
- 同じ対象を調べるのは `PATROL_CHECK_INTERVAL_HOURS` ごと（既定 6 時間）
- 読めないページを見回り係に任せるのは1日に1回まで

使った費用は実行の記録の `costCents` とログ（`kind: "patrol_collected"`）で見られます。ログには分類・件数・費用・所要時間だけを残し、ページの文章と利用者の ID を残しません。

## CI/CD

main ブランチには直接 push しません。人の変更も自動の更新も、同じ PR の検査を通ってから入ります。

| ワークフロー           | きっかけ                        | 中身                                                                                                                                                                                                                                                                                                                                     |
| ---------------------- | ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ci.yml`               | PR、main への push              | lint・typecheck・test・validate-data・build・e2e（接客サーバーのモックにつなぐ）・docker（イメージをモックで動かす）・secrets（gitleaks）・actionlint・dependency-review を別々のジョブで走らせ、「検査とビルド」で結果をまとめる。ジョブの中身は [開発の流れ](../development.md#5-ci)                                                   |
| `codeql.yml`           | PR、main への push、毎週        | CodeQL でコードとワークフローを解析する                                                                                                                                                                                                                                                                                                  |
| `deploy.yml`           | main への push                  | コミットの SHA のタグでイメージを作る → イメージをモックで動かし、`/healthz`・サンプルの相談・しおりの PDF・3D のモデルを確かめる（`scripts/smoke-mock.mjs --pdf --glb`） → 新しい版を通信なしで置き（タグ `candidate`）、外から確かめる（`scripts/check-deployed.mjs`） → 通信を切り替え、公開の URL を外から確かめる。下の「デプロイ」 |
| `rollback.yml`         | 手で起動（`workflow_dispatch`） | 指定した版に通信を戻し、公開の URL を外から確かめる。下の「前の版に戻す」                                                                                                                                                                                                                                                                |
| `update-festivals.yml` | 毎週・手で起動                  | 週次の調査の準備と回収。調査は Managed Agents の定期実行が行い、取り込める結果を PR にする。上の「祭りのデータの更新」                                                                                                                                                                                                                   |

- GitHub Actions の外部のアクションは、コミットの SHA で指定する
- 同じ更新のジョブが重ならないよう、同時に動かさない設定（`concurrency`）を入れる
- main ブランチは保護し、CI が通らない PR はマージできないようにする。履歴を読みやすく保つため、squash merge にする
- 依存パッケージは Dependabot で毎週確かめる
- GitHub のリポジトリの設定（秘密情報の検出と push の保護、脆弱性の非公開の報告と通知、main の保護と必須の検査、マージの方法、ラベル）は、[`scripts/setup-github.sh`](../../scripts/setup-github.sh) で入れて確かめる。Claude Code では `setup-github-repo` スキルから使える

## 実行の環境

| 項目       | 方針                                                                                                                   |
| ---------- | ---------------------------------------------------------------------------------------------------------------------- |
| 実行       | Cloud Run のコンテナ1つ。1日の相談の回数の上限をインスタンスごとに数えるので、インスタンスの数を1に固定する            |
| コンテナ   | Node 24 の Debian 系スリム版。管理者でないユーザーで動かし、書き込めるのは `/tmp` だけ                                 |
| 秘密情報   | Secret Manager。CI からは Workload Identity 連携で認証し、鍵のファイルを作らない                                       |
| 旅程の保存 | 旅程の版・しおりの共有・相談の途中の状態を Firestore に残し、しおりの URL はそれを読む（[ログインと保存](account.md)） |
| 外への通信 | 下の「外への通信の制限」を満たす                                                                                       |

認証の分け方は [ADR 0004](../adr/0004-authentication.md) にあります。

### Cloud Run の設定

サービスの設定は Cloud Run の側に置き、デプロイ（`deploy.yml`）ではイメージを差し替えます。インスタンスの数（最小 0・最大 1）と、`MATSURI_AGENT_MODE=live`・`MATSURI_STORAGE=firestore`・`FIREBASE_PROJECT_ID` は、コンソールで変わっていても動きが変わらないよう、デプロイのたびに版に付け直します。

| 項目               | 値                                                                                                                                                | 理由                                                                                                                                                                                 |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 実行環境           | 第2世代                                                                                                                                           | Agent SDK のバイナリと Chromium を、ふつうの Linux と同じように動かす                                                                                                                |
| インスタンスの数   | 最小 0・最大 1                                                                                                                                    | 1日の相談の回数と同時に返事を作る数の上限を、インスタンスごとに数えるため。相談の続きと旅程は Firestore にあるので、別のインスタンスにも届く。使われていない間は止めて費用をかけない |
| CPU とメモリ       | 1 vCPU・2 GiB。CPU はリクエストを処理している間だけ割り当てる                                                                                     | Agent SDK のバイナリを同時に数本動かす                                                                                                                                               |
| タイムアウト       | 300 秒                                                                                                                                            | SSE の返事を最後まで届ける                                                                                                                                                           |
| 同時のリクエスト   | 40                                                                                                                                                | 画面のファイルと API をまとめて受ける。live の返事の数は `MAX_CONCURRENT_TURNS` で別に絞る                                                                                           |
| 起動の確認         | `/healthz` に HTTP で                                                                                                                             |                                                                                                                                                                                      |
| 公開               | 認証なしで呼べる（`/api/*` は合言葉で守る）。VPC への外向きの接続は付けない                                                                       |                                                                                                                                                                                      |
| サービスアカウント | 実行用の専用のアカウント。`ANTHROPIC_API_KEY` と `ACCESS_PASSCODE` のシークレットを読むことと、Firestore の読み書き（`roles/datastore.user`）だけ | 乗っ取られても、できることを小さくする。既定の Compute のアカウントは使わない                                                                                                        |
| 秘密情報           | Secret Manager から環境変数として渡す                                                                                                             | 値をイメージ・リポジトリ・ログに出さない                                                                                                                                             |
| イメージ           | Artifact Registry。最新の10版を残し、1日より古いものは消す                                                                                        |                                                                                                                                                                                      |

- 本番の環境変数：`NODE_ENV=production`・`MATSURI_AGENT_MODE=live`・`MODEL_CONCIERGE`・`MODEL_STAFF`・`MODEL_PLANNER`・`MODEL_EVALUATOR`・`MODEL_VERIFIER`・`MODEL_WISH_READER`（省略可）・`DAILY_CHAT_LIMIT`・`DAILY_CHAT_LIMIT_PER_IP`・`AGENT_MAX_BUDGET_USD`・`MAX_CONCURRENT_TURNS`・`TRUSTED_PROXY_HOPS=1`・`MATSURI_STORAGE=firestore`・`FIREBASE_PROJECT_ID`・`FIREBASE_WEB_API_KEY`・`FIREBASE_AUTH_DOMAIN`。`PORT` は Cloud Run が渡す
- Firestore・TTL・セキュリティルール・Firebase Authentication・実行用のアカウントの権限は、[`scripts/setup-firestore.sh`](../../scripts/setup-firestore.sh) で入れて確かめる（[ログインと保存の仕様](account.md#google-cloud-の設定)）
- Cloud Run の既定の URL（`run.app`）では、末尾が `z` のパスが外から届かない。外からの死活監視には `/health` を使う
- しおりの PDF を作るときは、コンテナに Chromium の headless shell と、`assets/shiori` の日本語フォントを入れる（Playwright の `playwright-core` はサーバーの依存なので、イメージには必ず入る。Dockerfile を見る）

### デプロイ

GitHub Actions から Workload Identity 連携でデプロイ用のサービスアカウントとして入り、鍵のファイルを作りません。

- Workload Identity 連携のプロバイダは、このリポジトリ（リポジトリと持ち主の ID で照合）の `refs/heads/main` からのトークンだけを受け付ける
- デプロイ用のアカウントの権限は、このサービスの `roles/run.developer`、イメージのリポジトリへの書き込み（`roles/artifactregistry.writer`）、実行用のアカウントとして動かす権限（`roles/iam.serviceAccountUser`）だけ
- ワークフローは、次の GitHub Actions の変数（`vars`）を読む。どれも秘密情報ではないが、ワークフローには書き込まない

| 変数                             | 内容                                            |
| -------------------------------- | ----------------------------------------------- |
| `GCP_PROJECT_ID`                 | Google Cloud のプロジェクト ID                  |
| `GCP_REGION`                     | Cloud Run と Artifact Registry のリージョン     |
| `CLOUD_RUN_SERVICE`              | Cloud Run のサービス名                          |
| `ARTIFACT_REGISTRY_REPOSITORY`   | イメージを置く Artifact Registry のリポジトリ名 |
| `GCP_WORKLOAD_IDENTITY_PROVIDER` | Workload Identity 連携のプロバイダの完全な名前  |
| `GCP_DEPLOY_SERVICE_ACCOUNT`     | デプロイ用のサービスアカウントのメールアドレス  |

#### 出し直す

デプロイは、順番が来た時点で main の先頭のコミットだけを出します。先頭でないコミットは飛ばすので、本番が前のコードに戻りません。

失敗したデプロイを出し直すときは、古い実行の再実行（`gh run rerun`）ではなく、次のコマンドで main の先頭を出します。古い実行を再実行すると、順番を待っている新しいデプロイが取り消されることがあります。

```bash
gh workflow run deploy.yml --ref main
```

前のコードに戻したいときは、[前の版に戻す](#前の版に戻す)の手順を使います。

#### デプロイで確かめること

| いつ                           | どこに                         | 確かめること                                                                                                                                                                                                              |
| ------------------------------ | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| イメージを作ったあと           | ランナーの上で、モックで動かす | `/healthz`、サンプルの相談が最後まで通る、旅程としおりが開ける、しおりの PDF が作れる、3D のモデル（GLB）が配られる                                                                                                       |
| 新しい版を通信なしで置いたあと | タグ `candidate` の URL        | `/health`、画面が配られる、3D のモデルが届く、相談の API が合言葉で守られている（合言葉なしで 401。サービスに合言葉を設定していないときは、守られていないことを知らせるだけ）、しおりの経路が動いている（ない旅程は 404） |
| 通信を切り替えたあと           | 公開の URL                     | 上と同じ                                                                                                                                                                                                                  |

置いた版は live で動くので、外からは費用のかかる相談を送りません。相談としおりの PDF は、同じイメージ（同じダイジェスト）をデプロイの前にモックで確かめます。

### 前の版に戻す

- **自動**：通信を切り替えたあとの確かめに失敗すると、`deploy.yml` が切り替える前に通信を受けていた版へ通信を戻し、失敗で終わる。切り替える前に失敗したときは、通信は前の版のまま。通信はその版に固定されるので、次に成功するデプロイまで、手で新しい版を作っても通信は移らない
- **手で**：あとから不具合に気づいたときは、GitHub の Actions の画面で `rollback.yml`（前の版に戻す）を main で起動し、戻す先の版の名前を入れる。版の名前は Cloud Run のコンソールの「リビジョン」か、次のコマンドで調べる

```bash
gcloud run revisions list --service "$CLOUD_RUN_SERVICE" --region "$GCP_REGION" --limit 10
```

- 戻したあとも、次に main へ入った変更のデプロイで、通信はまた新しい版に向く。直すまでデプロイを止めたいときは、直す PR をマージするまで main に入れない
- GitHub Actions が使えないときは、デプロイ用の権限を持つアカウントで次を実行する

```bash
gcloud run services update-traffic "$CLOUD_RUN_SERVICE" --region "$GCP_REGION" --to-revisions "<戻す先の版>=100"
```

- イメージは最新の10版を残すので、戻せるのはその範囲。3D のモデルをコンテナに入れる前の版に戻すと、外からの確かめ（3D のモデル）は落ちる

### 利用者の IP（`TRUSTED_PROXY_HOPS`）

Cloud Run の既定の URL（前にロードバランサーを置かない）では、`TRUSTED_PROXY_HOPS=1` にします。実機で確かめた届き方は次のとおりです。

- コンテナから見た接続の相手は、どの利用者でも Cloud Run の前段のアドレス（リンクローカル）になる。0 にすると全員が同じ IP として数えられ、IP ごとの上限が全員にまとめて効いてしまう
- 前段は、利用者が送った `X-Forwarded-For` を消さずに残し、その右に実際の接続元の IP を1つ足す（利用者が `1.2.3.4` を送ると、`1.2.3.4,<接続元>` で届く）
- そのため、信用できるのは右から1つ目だけ。2 以上にすると、利用者が書いた値を IP として使ってしまう

前に外部の HTTPS ロードバランサーを置くときは、ロードバランサーも1つ足すので、置いたあとに確かめ直して数を変えます。

### 外への通信の制限

再確認のエージェントは、公開の Web のページを読みに行きます（WebFetch）。読みに行く前に、URL の形（`checkPublicWebUrl`）と、名前を解決した先のアドレスがプライベート・ループバック・リンクローカル（クラウドのメタデータを含む）でないことをフックで確かめます。ただし、確かめたあとに名前の向き先を変えられる（DNS リバインディング）ことまではコードでは防げないので、実行の環境で次を要件にします。

- コンテナから、内側のネットワーク（プライベートのアドレス、ループバック、リンクローカル、メタデータサーバー）への通信を、ネットワークの設定で止める。VPC の中のサービスへつながない（VPC への外向きの接続を付けない）
- 外へ出てよいのは、Anthropic の API、気象庁の予報、公開の Web（HTTP・HTTPS）だけ
- Cloud Run では、メタデータサーバーへの通信はネットワークの設定では止められない（サービスアカウントのトークンをここから受け取るため）。VPC への外向きの接続を付けないことで内側のネットワークには届かないようにし、メタデータについては次のサービスアカウントの権限の絞り込みで補う
- サーバーのサービスアカウントには、Firestore の読み書き（`roles/datastore.user`）より強い権限を持たせない（メタデータからトークンを取られても、できることを小さくする）

## 環境変数

| 変数                                                                                   | 内容                                                                                                                                                                           |
| -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `PORT`                                                                                 | サーバーのポート。開発中は、画面の開発サーバーもこのポートへ中継する                                                                                                           |
| `MATSURI_WEB_PORT`                                                                     | 開発中の画面のポート（省略時は 5173）。ふさがっていたら、ずらさずに止まる                                                                                                      |
| `MATSURI_AGENT_MODE`                                                                   | `mock`（記録の再生）/ `live`（Agent SDK）                                                                                                                                      |
| `ANTHROPIC_API_KEY`                                                                    | Claude の API キー（live のとき）                                                                                                                                              |
| `MODEL_CONCIERGE`・`MODEL_STAFF`・`MODEL_PLANNER`・`MODEL_EVALUATOR`・`MODEL_VERIFIER` | 役割ごとのモデル名（[モデルの割り当て](agents.md#モデルの割り当て)）                                                                                                           |
| `MODEL_WISH_READER`                                                                    | 祭りから探すときの自由記述の読み取りのモデル名。省略時は軽いモデルの別名 `haiku`（[自由記述の読み取り](agent-runtime.md#自由記述の読み取り)）                                  |
| `ACCESS_PASSCODE`                                                                      | 公開している URL の合言葉。画面からはヘッダー `x-access-passcode` で送る                                                                                                       |
| `DAILY_CHAT_LIMIT`                                                                     | 1日（日本の日付）の相談の回数の上限。空か 0 なら上限なし                                                                                                                       |
| `AGENT_MAX_BUDGET_USD`                                                                 | live の1回の発言の費用の上限（米ドル、Agent SDK の推定で判定）                                                                                                                 |
| `MATSURI_FESTIVALS_DIR`                                                                | 祭りのデータを読む場所（`path.delimiter` で区切って複数）。省略時、mock は架空の祭り（`data/samples/festivals`）、live は `data/festivals`（空なら、本番でなければ架空の祭り） |
| `MATSURI_REPLAY_SPEED`                                                                 | mock の再生の速さの倍率（1 で記録どおり、2 で2倍速、0 で待たない）                                                                                                             |
| `MATSURI_WEB_DIST`                                                                     | 同じオリジンから配る画面のビルドの場所。本番の既定は `apps/web/dist`                                                                                                           |
| `DAILY_CHAT_LIMIT_PER_IP`                                                              | 1日の相談の回数の、利用者ごと（ログインしていなければ IP ごと）の上限。空か 0 なら上限なし                                                                                     |
| `MAX_CONCURRENT_TURNS`                                                                 | live で同時に返事を作る数の上限（既定 4）。超えた発言は 503 で断る                                                                                                             |
| `MAX_CONCURRENT_TURNS_PER_CLIENT`                                                      | live で同時に返事を作る数の、利用者ごと（ログインしていなければ IP ごと）の上限（既定は全体の半分を切り上げた数）。超えた発言は 503 で断る                                     |
| `INTERNAL_OIDC_AUDIENCE`・`INTERNAL_OIDC_CALLER_EMAIL`                                 | 内部の入口の OIDC の検証（[内部の入口](api.md#内部の入口)）。両方がそろったときだけ使う。省略できる                                                                            |
| `ANTHROPIC_WEBHOOK_SIGNING_KEY`                                                        | 内部の入口の Webhook の署名の鍵（`whsec_…`）。省略できる。本番では Secret Manager から渡す                                                                                     |
| `PATROL_ANTHROPIC_API_KEY`                                                             | 見回り係のセッションを作る API キー（定義を置いたワークスペースのもの）。省略できる。なければ見回りの入口だけが断る。本番では Secret Manager から渡す                          |
| `PATROL_SESSION_BUDGET_USD`・`PATROL_MAX_TARGETS`・`PATROL_CHECK_INTERVAL_HOURS`       | 見回りのセッションの予算（既定 2、上限 10）、1回に調べる対象の数（既定 20、上限 20）、同じ対象を調べる間隔（既定 6）。読めない値は既定にする                                   |
| `TRUSTED_PROXY_HOPS`                                                                   | 利用者との間のプロキシの数。`X-Forwarded-For` の右から数えて利用者の IP を決める。Cloud Run の既定の URL では 1（上の「利用者の IP」）                                         |
| `MATSURI_STORAGE`                                                                      | 旅程・共有・相談の途中の状態の保存先。`memory`（既定。再起動で消える）/ `firestore`                                                                                            |
| `FIREBASE_PROJECT_ID`                                                                  | Firebase（Google Cloud）のプロジェクト ID。Firestore とログインに使う                                                                                                          |
| `FIREBASE_WEB_API_KEY`・`FIREBASE_AUTH_DOMAIN`                                         | Firebase のウェブアプリの公開の設定。プロジェクト ID と3つそろうと、画面にログインを出す                                                                                       |
| `FIRESTORE_DATABASE_ID`                                                                | Firestore のデータベースの ID（省略時は `(default)`）                                                                                                                          |
| `FIRESTORE_EMULATOR_HOST`・`FIREBASE_AUTH_EMULATOR_HOST`                               | 手元のエミュレーターにつなぐとき（[ログインと保存](account.md#手元で動かす)）                                                                                                  |

しおりの PDF の変数（`MATSURI_SHIORI_PDF_*`・`MATSURI_SHIORI_CHROMIUM_PATH`・`MATSURI_SHIORI_ASSETS_DIR`）は [旅のしおりの仕様](shiori.md) にあります。

値は、手元ではリポジトリのルートの `.env` に書くかシェルの環境変数で渡し（`pnpm dev` と `check:live` は `.env` があれば読み、シェルの値を優先します）、本番ではクラウドの秘密情報の管理に置きます。本番のイメージは `.env` を読みません。[`.env.example`](../../.env.example) には変数名と説明だけを書きます。

本番（`NODE_ENV=production`）の live では、`ACCESS_PASSCODE`・`DAILY_CHAT_LIMIT`・`AGENT_MAX_BUDGET_USD`・`ANTHROPIC_API_KEY` のどれかが欠けているか、`MATSURI_STORAGE` が `firestore` でないと、サーバーは起動しません。保存先がメモリのままだと、デプロイや停止のたびに相談の途中の状態と共有のしおりが消えるためです。起動しない版には通信が切り替わらないので、前の版が動き続けます。

### メモリに置くものの上限

| もの                 | 上限                                                                              |
| -------------------- | --------------------------------------------------------------------------------- |
| 相談                 | 1000件。超えたら、いちばん長く使われていない相談から消す。6時間使われなければ消す |
| 旅程（手元の写し）   | 最後に保存してから30日で消す。5000件を超えたら、古いものから消す                  |
| 保存先がメモリのとき | 旅程・共有・相談の途中の状態を、それぞれ5000件まで。超えたら古いものから消す      |
| 1日の回数の数え      | 日本の日付が変わったら数え直す                                                    |

## セキュリティ

| 脅威                                               | 対策                                                                                                                                                                                                                                                 |
| -------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| API キーの漏えい                                   | 秘密情報の管理にだけ置き、ブラウザとリポジトリには出さない。CI で gitleaks を回す                                                                                                                                                                    |
| 使いすぎによる費用の増大                           | 合言葉、1日の相談の回数の上限、利用者ごと（ログインしていなければ IP ごと）の回数の上限、Anthropic のコンソールでの利用額の上限                                                                                                                      |
| 利用者からのプロンプトインジェクション             | 接客エージェントに渡すツールを絞る。組み込みのファイル操作やシェルは使わせず、8つのカスタムツールだけを許す。Web の検索と取得は、ツールの中で開催を確かめる1回きりの `query()` にだけ渡す。乗っ取られても、できることがない状態にする                |
| Web ページを経由したインジェクションとデータの汚染 | ページを読む役と書く役を分け、セッションに秘密の値も権限も置かない。報告は決まった項目だけを受け取り、コードで確かめる（上の「プロンプトインジェクションへの備え」）。開催日の変更や新しい祭りは人が確かめる。公式以外の情報源だけでは確度を上げない |
| サーバーの内側を取りに行かされる                   | エージェントが取りに行く URL を、フックで公開の Web だけに限る（IP アドレスの直接指定、内側向けの名前、ポート番号、ユーザー名つきの URL を断る）                                                                                                     |
| 読んでいないページを出典にする                     | 再確認の出典が、実際に読んだページかを照合する。読んでいない出典は捨て、公式の出典が残らなければ「予定どおり」にしない                                                                                                                               |
| 見回りの入口を外から呼ばれる                       | 起動は OIDC、Webhook は署名を確かめる。確かめられなければ処理を始めない。設定がなければその入口だけが断る（上の「入口の決まり」）                                                                                                                    |
| 見回りのページで通知を偽られる                     | 見回り係に利用者の情報と権限を渡さない。報告の値は、コードで読み直した行にあるときだけ認め、変化の種類はコードが決める。通知にページの文章を入れない（上の「検問」）                                                                                 |
| 画面への不正なスクリプト（XSS）                    | 祭りのデータとモデルの文章は必ず文字列として表示し、HTML として埋め込まない。Content-Security-Policy で、読み込める先を自分のドメインと地図のタイルに限る                                                                                            |
| コンテナの乗っ取り                                 | 管理者でないユーザーで動かす。書き込めるのは `/tmp` だけにし、Agent SDK の作業場所もそこに置く                                                                                                                                                       |
| 権限の強すぎるアカウント                           | サーバーのサービスアカウントは Firestore の読み書きだけ。デプロイのアカウントはデプロイだけ。調査する側には GitHub の権限を渡さない                                                                                                                  |
| 他人の旅を読む・消す                               | 利用者は Firebase の ID トークンをサーバーで確かめて決める。旅の API は持ち主にだけ答え、ほかの人には 404 を返す。旅を残すときは相談の ID で指す。ブラウザから Firestore へは読み書きさせない                                                        |
| サプライチェーン                                   | lockfile で固定し、GitHub Actions の外部のアクションはコミットの SHA で指定する                                                                                                                                                                      |
| サイトへの迷惑                                     | 調査のスキルで利用規約と robots.txt を守り、同じサイトへのアクセスに間隔を空ける                                                                                                                                                                     |

## 個人情報

- 出発地は駅名までにとどめ、住所は聞かない
- 会話の全文はログに残さない。ログにはツールの呼び出しと所要時間だけを残す
- ログインは、旅を残す・あとで開く・消すときだけ。Google のアカウントの名前とメールアドレスは Firebase Authentication に残り、Firestore には利用者の ID だけを置く
- 会話の全文は残さない。相談の途中の状態（条件・こだわり・候補・旅程の ID・段階）は6時間で消す
- ログインせずに作った旅程と、共有のしおりは30日で自動的に消す。残した旅は、利用者が消すまで残す
- 利用者は、旅を1つずつ、または旅とログインの記録をすべて、画面から消せる
