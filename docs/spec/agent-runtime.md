# 接客エージェントの実行の仕様

Claude Agent SDK（TypeScript）で接客エージェントを動かすときの決まりです。設定の名前は、lockfile で固定した SDK の型定義で確かめてあります。SDK の版を上げたら確かめ直します。

役割・会話の流れ・ツールの中身は [接客エージェントの仕様](agents.md) にあります。ここでは「どう動かすか」を決めます。

## 方針

1. **できることを、必要な分だけに絞る。** 利用者の発言や読んだページで指示を上書きされても、できることがない状態にする
2. **決まった計算と検証はコード、判断は Claude。** 日程・所要時間・営業時間・出典の照合はツールの中のコードで行う
3. **外から来た文字列はデータとして扱う。** 祭りのデータ、Web のページ、利用者の発言、前の返答を、指示として読ませない
4. **失敗は分類し、直りうるものだけを試し直す。** 直らなければ、利用者に短く伝えて止まる

| `systemPrompt`       | 変わらない部分を前に置く（下の「プロンプトキャッシュ」）                                           | 変わらない部分をキャッシュに乗せる                                                                                                                                                                                                                                                                    |

### 会話の続き

続きの発言を同じ SDK のセッションで受けるには、会話の記録が要ります。

- 記録を残さない（`persistSession: false`）なら、発言ごとに、サーバーが持つ旅の条件と旅程の要約をプロンプトに入れて、新しいセッションで答える
- 記録を残すなら、保存先（`CLAUDE_CONFIG_DIR`）を一時ディレクトリの下にし、セッションが終わったら消す。会話の全文をログや外部の保存先に出さない
- 手元の開発で、ログイン済みの Claude Code の資格情報を使うときは、資格情報が既定の置き場所にあるので保存先を変えない（API キーで動かす場面では、上のとおり一時ディレクトリにする）

### プロンプトキャッシュ

変わらない部分（守るルール・口調・ツールの使い方）と、相談ごとに変わる部分（今日の日付・聞き取れた条件・旅程）を分け、変わらない部分を前に置きます。前に置いた部分は、ほかの相談とキャッシュを共有できます。分け方は次のどちらでもかまいません。

- system prompt はまったく変わらない文字列にし、相談ごとに変わるものは発言のプロンプトに入れる。スタッフには `SubagentStart` のフックの `additionalContext` で渡す
- `systemPrompt` を文字列の配列にし、`SYSTEM_PROMPT_DYNAMIC_BOUNDARY` で分ける

```ts
systemPrompt: [
  conciergeRules, // 守るルール・口調・ツールの使い方（変わらない）
  SYSTEM_PROMPT_DYNAMIC_BOUNDARY,
  `今日は ${today} です。`, // 今日の日付、聞き取れた条件など（相談ごと）
];
```

3人のスタッフは、共通の前置き（祭りのデータの扱い、外から来た文字列の扱い）を一字一句同じ文字列にしてから、それぞれの担当を書き足します。

## ツール（プロセス内の MCP サーバー）

ツールは `tool()` と `createSdkMcpServer()` で定義し、入力の形は `packages/schema` の Zod から組み立てます。ハンドラーは、どれも共通の包みに通します。

1. **時間の上限で打ち切る。** `note_conditions` は5秒、`get_access`・`get_weather` は10秒、`update_itinerary` は評価係の採点（50秒で打ち切る）を含めて75秒、`search_lodging` は空室検索と宿の調べを含めて95秒、`research_route` は40秒、`research_trip` は経路と寄り道の調べを並べて100秒、`search_festivals` は候補の確かめを含めて70秒、`verify_festival` は70秒、`search_nearby` は寄り道の調べ（2回まで）を含めて95秒（[API の仕様](api.md#時間の上限)）。`createSdkMcpServer()` の `timeout`（SDK が呼び出しを打ち切る外側の上限）は、いちばん長いツールの上限より15秒長くし（110秒）、ツールの上限で止めたときの理由がエージェントに届くようにする。相談の進みのない時間の上限（90秒）より長いツールは `search_nearby`・`search_lodging`・`research_trip` で、中の調べが進むたびに `ToolContext.progress` で進みを知らせるので、動き続けている調べは止めない
2. **例外を投げない。** 失敗は `{ content: [{ type: "text", text: 理由 }], isError: true }` で返す。Claude は理由を読んで、代わりの案を出す
3. **結果はデータとして返す。** JSON の文字列にし、指示の文章を混ぜない
4. **サーバーの値を使う。** 今日の日付やセッションは、モデルの入力を信じず、サーバーが持つ値を使う。モデルに書かせた ID で、別の相談のデータを読ませない

## フック

フックは SSE のイベントを出す場所であり、安全のための関所でもあります。接客のエージェントと、開催を確かめる1回きりの `query()` とで、別のフックを渡します。

接客のエージェント（`apps/server/src/agent/hooks.ts`）：

| 契機                 | すること                                                                                                                                                           |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `SubagentStart`      | `staff.start` を出し、スタッフに相談の要点を渡す                                                                                                                   |
| `PreToolUse`         | `tool.start` を出す（吹き出しは決まった型から作る）。スタッフとツールの組み合わせ、スタッフを呼ぶ回数、`verify_festival` の回数を確かめ、外れたら断る              |
| `PostToolUse`        | `tool.end` を出し、続けて `itinerary.updated`・`festival.verified` を出す                                                                                          |
| `PostToolUseFailure` | 失敗した `tool.end` を出す                                                                                                                                         |
| `SubagentStop`       | 旅程係が、評価の基準に届かないまま（評価の回数が残っているのに）終えようとしたら、`{ decision: "block", reason }` で作り直しに戻す。戻すのは評価の上限の回数−1まで |

開催を確かめる `query()`（`apps/server/src/agent/webVerifier.ts`。確定前の再確認と、候補を出す前の確かめ）：

| 契機                     | すること                                                                         |
| ------------------------ | -------------------------------------------------------------------------------- |
| `PreToolUse`（WebFetch） | `checkPublicWebUrl` と、名前を解決した先のアドレスの確認を通し、通らなければ断る |
| `PostToolUse`            | `WebSearch`・`WebFetch` を `createWebActivityLog` に控える                       |
| `Stop`                   | 検索だけして本文を読んでいなければ、1回だけ続けさせる                            |

- 断るときは `{ hookSpecificOutput: { hookEventName: "PreToolUse", permissionDecision: "deny", permissionDecisionReason: 理由 } }` を返す。続けさせるときは `{ decision: "block", reason: 理由 }` を返す。形は SDK の型（`HookJSONOutput`）に合わせ、テストで確かめる
- 続けさせる回数には上限を置く。`stop_hook_active` は一度続けさせたあと立ちっぱなしになるので、上限の代わりにならない
- フックは素早く返す。SSE を送り終えるのを待たない
- フックの時間の上限（matcher の `timeout`、秒）は、フックの中で待つ時間より長くする。短いと、SDK がフックを打ち切る

## 確定（verify_festival）と、確かめ直すとき

開催は候補を出す前に確かめます（次の「候補を出す前の確かめ」）。旅程まで組んだあとで開催しないと分かると、それまでの相談がむだになるからです。利用者が「決定」と言ったときは、旅程を確定してしおりを作るだけにし、ふつうは調べ直しません。

- `verify_festival` は、旅程の `verification` に結果があればそれで、なければ主役の祭りとその日の候補の確かめの結果（とってあるもの）で確定し、旅程の `verification` に書く（`reused: true`。Web は使わない。`knownVerification`）
- 旅程は、決定するまで `verification` を確認前のままにする。しおりは決定のあとに出す
- どちらの結果もないとき（行く日を変えた、確かめの上限に達した、とっておく時間が過ぎたなど）だけ、下の手順で Web で確かめる

「公式情報で確認しました」と言うには、その出典のページを実際に読んでいる必要があります（情報の壁）。

1. ツールの中で、Web の検索と取得だけを許した1回きりの `query()` を動かす（`tools: ["WebSearch", "WebFetch"]`、MCP サーバーなし、記録を残さない）。読んだページの中の指示には従わないよう、プロンプトに書く
2. 結果は JSON で返させ、`parseJsonWithSchema` で取り出す。取り出せなければ、`buildJsonRetryPrompt` で1回だけ差し戻す（差し戻しではツールを使わせない）。時間の上限（70秒）は、差し戻しも含めた全体の予算として扱う
3. 返ってきた出典が、実際に読んだページかを `ungroundedSources` で確かめる。読んでいない出典は捨てる
4. 結果は3段階にする。公式の出典（祭りのデータで公式としたホストか、自治体のサイト）に今年の開催が書かれていれば「予定どおり」（`as_planned`）。公式の出典に例年の日程しかないとき、または公式以外の情報源に今年の開催が書かれていたときは「要事前確認」（`needs_check`）。どの情報源にも開催の情報がなければ「確認できず」（`not_found`）
5. 今年の開催と書かれていたか（年が書かれていたか）は、調べた側に申告させず、コードで決める（`yearStatedOnPage`）。
   - 調べた側には、ページに書かれている開催日の文を、年を補わずにそのまま写させる（`dateText`）
   - 写した文が、出典に残したページの本文（エージェントが受け取った WebFetch の結果）の中になければ、言い換えたか補ったとみなし、年は書かれていなかったことにする。照合では全角と半角・空白の違いだけをならす
   - 写した文に、確かめる日の年が西暦（2026）か令和（令和8年・令和八年）で書かれていれば、年が書かれていたとする。「毎年」「例年」や2桁の年（26年）は書かれていないとみなす
   - 文がない、照合できない、年がないときは、年は書かれていなかったことにする（推測で「予定どおり」にしない）。公式の出典なら「要事前確認」、公式以外の出典だけなら「確認できず」にする
6. Web で「確認できず」になっても（時間切れ・失敗を含む）、祭りのデータのその日の開催回が「発表済み」で、確度が公式の出典を最近（`DATA_CONFIRMATION_MAX_AGE_DAYS`、60日以内）確かめてあれば、その出典で「予定どおり」にする（`dataSources`）。公式以外の出典だけなら、「確認できず」を「要事前確認」にする。主催者のチラシやページで当年の日程を確かめたデータを、Web で読んだページに年がないことだけで捨てないため。変更・中止の知らせは、Web の結果を優先する
7. 「要事前確認」の旅程は（引き継いだ結果でも）、表紙と画面に「出発の前に主催者の案内で確かめる」と必ず出したしおりにして渡す。「確認できず」のときはしおりにせず、ほかの候補に戻る（候補を出す前に情報の取れない祭りは外してあるので、ふつうは起きない）

### 検索の言葉と情報源の順

小さな祭りほど、名前の書き方や地域の呼び方が揺れ、当年の日程は主催者のページや自治体の広報誌の PDF に散らばります。確かめのたびに、コードで次のものを決めて渡します（`apps/server/src/domain/searchQueries.ts`）。

- 検索の言葉（`verificationQueries`、7つまで）：公式のサイトの中の検索、名前と年と「日程」、祭りの名前だけ、市町村の名前と名前、市町村の名前と名前と令和の年、名前と「広報」、名前の別の書き方と年。エージェントは、いくつかを1回の返答で並べて検索し、見つからなければ言葉を変えて探し直す（検索は6回まで、ページは3回まで）
- データの出典の順（`bySourcePriority`）：1. 主催者・神社・自治体の当年の案内、2. 観光協会・公式の地域イベント情報、3. 地域の広報誌の PDF、4. 地域のメディア・イベントサイト、5. ブログ・SNS（手がかりにだけ使い、公式で確かめ直す）

## 候補を出す前の確かめ

祭りの候補を利用者に見せる前に、候補の開催日・時刻・状態（予定どおり・変更・中止）を、公式の情報で確かめます。データの更新のあとに発表された変更や中止を、提案の時点で拾うためです（情報の壁）。

1. `search_festivals` の中で、候補の祭りと日付ごとに、確定前の再確認と同じ1回きりの `query()` を動かす。結果は確定前の再確認と同じ手順（`parseJsonWithSchema`・`ungroundedSources`・`decideVerification`）で決め直す
2. 出す数（3件）の倍の6件を並べて確かめ、確かめた結果で選び直す（`pickVerifiedCandidates`）。中止と分かった祭りと、どこからも開催の情報が取れなかった祭り（`not_found`）は出さない。確かめられなかった（上限など）祭りは、データで確認済みのときだけ出す。公式で確かめられた祭りを先に、要事前確認、変更のあった祭りの順にする。1件の時間の上限は50秒で、超えたら「確認できず」にする（データの出典で確かめてあれば「予定どおり」か「要事前確認」）
3. 結果は祭りと日付ごとに6時間とっておき、ほかの相談でも使う。失敗や時間切れの結果はとっておかない。混雑・通信のような一時的な失敗（`@matsuri-ikoka/agent-kit` の `classifyFailure` で retryable）は、1件の時間の上限の中で1回だけやり直す。時間切れ・止められたとき・認証や費用の上限のようにやり直しても直らない失敗は、やり直さない
4. 1つの相談で新しく確かめるのは18件まで。費用は1件ごとに `AGENT_MAX_BUDGET_USD` を上限にする。モデルは `MODEL_STAFF`（確定前の再確認より件数が多いため）
5. 終わったものから `festival.verified`（`scope: "candidate"`、確かめた日 `date` つき）で画面に送る。候補には `check`（結果と確かめた時刻）を付け、公式の情報で確かめられたら確認済みにする。要事前確認の祭りは、画面で「要事前確認」と出し、選べるようにする
6. 要事前確認の祭りは、そのことと、出発の前に主催者の案内で確かめることを添えて出す。中止と分かった祭りはすすめない

## 行き方の調べ（research_route）

旅程は、利用者が伝えた出発の駅から始めます。祭りのデータにある主要駅は出発の駅ではないので、そこから始めると、実際より短い移動時間で組んでしまいます（計画の壁）。

1. 出発の駅から会場までの所要時間の目安は、駅の位置（[出発の駅の一覧](../stations.md) の `data/stations/points.json`）からコードで見積もる（`estimateTravel`）。出発の駅がデータの主要駅（またはそのすぐ近くの駅）なら、データの所要時間を使う。同じ名前の主要駅がほかの土地にもあるときは、会場に近い方を使う
2. `research_route` の中で、Web の検索と取得だけを許した1回きりの `query()` を動かし、出発の駅から会場の最寄り駅までの乗る路線・乗り換え・所要時間の幅を調べる（`apps/server/src/agent/webRouteResearcher.ts`）。動かし方（WebFetch の宛先の確認・JSON の差し戻し・読んだページだけを出典にする）は確定前の再確認と同じ。時間の上限は40秒、結果は駅の組ごとに24時間とっておく
3. 調べた所要時間は、駅の位置からの見積もりと照らし（`checkResearchedMinutes`）、見積もりの下限の7割より短いもの、上限の1.5倍と30分より長いものは、区間の取り違えとみなして使わない。その場合と、調べられなかったときは、見積もりを返す
4. `update_itinerary` は、旅程の出発地を相談の出発の駅にそろえ、1日目の最初の予定が出発の駅からの移動でないもの（`start_not_origin`）と、1日目に主役の祭りへ向かうとき、はじめに続く移動の時間の合計が見積もりの下限の7割より短いもの（`origin_move_too_short`）は保存しない。日帰り（0泊）で片道の上限（`maxTravelMinutes`）を言われているときは、上限を必ず守る条件として、1日目のはじめに続く移動の時間の下限の合計が上限を超えるもの（`over_travel_limit`）も保存しない（下限が収まり上限が超える境目のものは、候補と同じく残す）

帰りの行き方（`direction: "return"`）は、会場の最寄り駅から終わりの駅（`returnTo`、なければ出発の駅）までの乗り換えの区間と、その日のうちに帰れる最終の時刻（`lastDeparture`）を調べる。最終は時刻表か乗り換え案内のページで読めたときだけ返し、分からなければ `null` にする（旅程では帰りの最終が分からないとして不足に残る）。区間（`legs`）は、出発の駅から着く駅までつながっているときだけ使う。行きと帰りは別にとっておき、調べ直し（`focus` つき）はとっておいた結果を使わない。調べたページは相談に残し（`researchedSources`）、旅程の移動と帰りの最終の出典として認める

## 旅程の調べを並べる（research_trip）

経路と食事・寄り道を1つずつ順に調べると時間がかかり、旅程係が調べを省くと、乗り換えや食事の抜けた旅程になります（計画の壁）。

1. `research_trip` は、行きの行き方・帰りの行き方（最終まで）・会場の周りの食事と寄り道（`search_nearby` と同じ調べ）を `Promise.all` で並べて動かす。`only` で係（`route`・`nearby`）を選べる。宿の調べ直しは `search_lodging` で行う
2. 係ごとの失敗は `@matsuri-ikoka/agent-kit` の `retryOnce` で分類し、時間をおけば直りうる失敗（混雑・通信・時間切れ）だけを1回自動でやり直す。やり直しても失敗した係は `failed` に名前を返し、ほかの係の結果は使う
3. 評価で調べ直しを頼まれたときは、頼みの文（`ask`）を `focus` に渡す。行き方の調べには「調べ直しで特に確かめること」として、寄り道の調べには確かめる観点の先頭に入れる。`meals` で昼・夜に絞ると、その時間帯の前後30分で探す

## 旅程の評価（update_itinerary の中）

旅程を組むモデルが自分で見直すだけでは、同じ見落としを重ねやすく、長い旅程の足りなさを正しく指摘できません。点検でそろっているべきものをコードで確かめ、別のモデルの評価係が観点ごとに採点し、点が届くまで調べ直して作り直します（[旅程の評価](itinerary.md#旅程の評価)、[設計判断の記録 0008](../adr/0008-plan-check-and-evaluation-loop.md)）。

1. `update_itinerary` は保存できた旅程の不足（`gaps`）と注意から、観点ごとのコードの点を出す（`scorePlan`）
2. 評価係（`apps/server/src/agent/planEvaluator.ts`、指示は `prompts/evaluator.md`）を、道具を持たない1回きりの `query()` で動かす。動かし方（開発環境から切り離す・JSON の差し戻し）は確定前の再確認と同じで、考える深さは medium。渡すのは、聞き取った条件の要約・採点に要るだけにした旅程（出典は数だけ）・点検の結果。モデルは `MODEL_EVALUATOR`（省略時は `MODEL_PLANNER`、それもなければ `MODEL_STAFF`）、費用は `AGENT_MAX_BUDGET_USD` を上限にし、50秒で打ち切る
3. 評価係の点（1〜5）は信用しない入力として 0〜100 にし、観点ごとにコードの点と低いほうを点にする。合否（すべての観点が70点以上）と調べ直しの頼み（足りない観点の係と、頼みの文）はコードで決める（`evaluatePlan`）。評価係の失敗は `retryOnce` で1回だけやり直し、だめなら点検の点だけで決める（`judgedBy: "code"`）。mock とテストには評価係がない
4. 評価は旅程に付けて保存し、ツールの結果の `next` で次にすることを返す。基準に届かず回数が残っていれば、`research_trip` を `only` と `focus` を付けて呼び、作り直して保存し直すよう伝える。評価は1回の発言で3回まで。3回で届かなければ、足りない点をそのまま報告させる
5. 旅程係が、基準に届かないまま報告して終えようとしたら、`SubagentStop` のフックで作り直しに戻す（上の「フック」）

## 寄り道の調べ（search_nearby）

祭りのデータの周辺の場所だけから選ぶと、データにない店は出せず、食べたいものに合う店がなくても手元の店で埋めてしまいます。行く日に休みの店を入れると、当日の動きが崩れます（計画の壁）。

1. `search_nearby`（祭りの ID で探すとき）の中で、Web の検索と取得だけを許した1回きりの `query()` を動かし、会場の周りの食事の店・観光・休憩の場所と、行く日の営業（定休日・営業時間・臨時休業の告知）を調べる（`apps/server/src/agent/webNearbyResearcher.ts`、指示は `prompts/nearby.md`）。動かし方（開発環境から切り離す・WebFetch の宛先の確認・JSON の差し戻し・読んだページだけを出典にする）は確定前の再確認と同じ。モデルは `MODEL_STAFF`、費用は `AGENT_MAX_BUDGET_USD` を上限にする。ターンの上限は、検索とページの読み込みを8回ずつ行い、言葉を変えて探し直せるよう16にする（確定前の再確認は10）
2. 調べ方（検索の言葉の作り方と、確かめる観点）はコードで決め（`apps/server/src/domain/nearbySearch.ts`）、毎回の依頼に必ず入れる。調べる係は開発環境から切り離すのでファイルのスキルは読めず、調べ方をモデルに任せると、料理の種類の大きな言葉（肉料理）のまま探して店の一覧に当たらないことがある
   - 検索の言葉は8つまで（並べて呼ぶ）。食べたいものを料理の名前に言い換え（肉料理 → 焼肉・ステーキ・ハンバーグ・とんかつ・焼き鳥・鉄板焼き など。ほかの種類も同じ）、会場の最寄り駅（祭りのデータの `access.stations`）・市町村・時間帯（使える時間帯が昼にかかればランチ、夜にかかればディナー）・同行者（子連れ）・車（駐車場）・食事の制限と組む。グルメの案内サイトの名前（食べログ・ホットペッパーグルメ・Retty）を足した言葉で、店の一覧のページも狙う。一覧のページからは、合いそうな店を複数拾い、店ごとのページで確かめてよい
   - 確かめる観点は、出す料理・営業時間とラストオーダー・定休日・臨時休業の告知・1人あたりの料金・会場からの位置。子ども連れなら子どもが入れるか、車なら駐車場、食事の制限があればその対応も足す
   - 探す範囲は、1回目は会場からおおむね2km（車なら5km）
3. 1回目で食べたいもの（屋台のほか）に合う店が1つも残らなければ、時間の残りが25秒以上あるときだけ、広げた調べ方で2回目を調べる。2回目は、会場の名前の「周辺」・隣の駅・都道府県と市町村・言い換えの残り・料理の種類の大きな言葉で探し、範囲を距離の上限（歩きなら3km、車なら10km）まで広げる。2回の結果は、名前と位置が同じ場所を1つにしてまとめる。何回調べたかは `research.rounds` で返す
4. 調べる係には、聞き取った食べたいもの・食事で気をつけたいこと・1人あたりの予算・同行者（子ども連れか）と、祭りのデータの周辺の場所（参考）、調べ方を渡す。結果は、祭り・日付・食の条件・予算・子ども連れか・調べ方（何回目か・範囲・検索の言葉）の組ごとに6時間とっておく（使える時間帯は含めず、時間帯はコードで絞る）
5. 返ってきた場所は信用しない入力として、コードで最後に絞る（`screenResearchedSpots`）。会場から距離の上限（歩きなら3km、車で回るなら10km。車かは、想定している交通手段の車・レンタカーか、こだわりの移動が車かで決める）より遠い場所、行く日が休みの場所、使える時間帯に営業が合わない場所、子ども連れで入れない店、1人あたりの料金の下限が1人あたりの予算の3割を超える店を除く。店は、食べたいもの（屋台のほか）に合う料理をページに書かれているものだけを残し、ベジタリアン・ヴィーガン・ハラールは対応するとページにある店だけ、生ものが苦手なら海鮮だけの店は除く。2回調べても合う店がなければ合わない店で埋めず、`research.foodFound: false` と「見つからなかった」ことを返す
6. 行く日に営業していると確かめられた場所は `openStatus: confirmed`、確かめきれなかった場所は `needs_check`（旅程では「営業は行く前に要確認」と書く）。出典は読んだページの URL と題名に、確かめた日を付け、ページが2つ以上なら確度を `corroborated`、1つなら `single` にする。要約は調べる係の言葉で書かせ、ページの文は写させない
7. 残した場所は `web-` で始まる ID を付けて相談に残し、`update_itinerary` は祭りのデータの場所と同じく、位置・営業時間・出典を入れ直して休業日と営業時間を照らす。相談を保存の口から戻したあとは、前の版の旅程に入っている調べた場所を使う
8. 調べは、1回目を55秒、2回目を含めた全体を85秒で打ち切る（ツールの上限は95秒）。1回目が上限を超えたとき・失敗したとき・ページを1つも読まなかったときは、祭りのデータの周辺の場所から選ぶ（`research.status: fallback`）。2回目が調べられなかったときは、1回目の結果を使う。調べの間は、中の Agent SDK の知らせが届くたびに相談の進みを知らせ（`ToolContext.progress`）、進みのない時間の上限（90秒）で止めない。mock とテストには調べる係がなく、祭りのデータの周辺の場所だけから選ぶ（`data_only`）

## 宿の調べ（search_lodging）

泊まる地域だけを書いた旅程では、祭りの夜にどの宿に泊まればよいかが分からず、混む夜に自分で探し直すことになります（計画の壁）。空室検索の API が使えないときも、具体的な宿を出典つきで提案します。

1. `search_lodging` は、空室検索（[宿の空き](agents.md#宿の空き)）で空きのある宿が見つかればそれを使う。キーがない・調べられない・空きがないときは、Web の検索と取得だけを許した1回きりの `query()`（宿の調べ役）を、観点ごとに並べて動かす（`apps/server/src/agent/webLodgingResearcher.ts`、指示は `prompts/lodging.md`）。動かし方（開発環境から切り離す・WebFetch の宛先の確認・JSON の差し戻し・読んだページだけを出典にする）は寄り道の調べと同じ。モデルは `MODEL_STAFF`、費用は1つの調べ役ごとに `AGENT_MAX_BUDGET_USD` を上限にし、ターンの上限は12
2. 観点と調べ方はコードで決め（`apps/server/src/domain/lodgingResearch.ts` の `lodgingSearchPlans`）、毎回の依頼に必ず入れる。会場の近く（会場の名前・市町村・祭りの名前と宿の言葉）と駅の近く（祭りのデータの `access.stations` の最寄り駅。なければ市町村）は必ず調べ、宿の予算が分かれば予算に合う宿、子ども連れなら家族向けの宿（添い寝・和室など）も調べる。検索の言葉は1つの観点に4つまで
3. 調べ役には、祭り・会場・泊まる日と泊数・人数・1泊1人あたりの宿の予算（泊まり全体の予算なら泊数で割る）と、その観点の調べ方を渡す。1つの観点が失敗しても、ほかの観点の結果を使う。結果は観点と条件の組ごとに6時間とっておく
4. 返ってきた宿は信用しない入力として、コードで突き合わせて選ぶ（`screenResearchedLodging`）。名前（全角・半角・空白・括弧の補足をならしたもの）が同じ宿を1つにまとめ、会場から10km より遠い宿、ページの料金の下限が1泊1人あたりの予算を超える宿、子ども連れで子どもを断る宿を除く。並びは、挙がった観点の数 → 予算に収まると分かる宿 → 子ども連れなら家族向け → 会場に近い順で、3件まで
5. 会場からの距離と移動の目安（2km までは徒歩、より遠ければバスやタクシー）はコードで計算する（`fromVenue`）。空室検索の宿にも同じく付ける。Web の宿は空きを調べていないので、1泊の合計は `null` にし、ページの料金の目安だけを持つ。出典は宿のページを先にし、読んだページが2つ以上なら `corroborated`、1つなら `single`
6. 調べは75秒で打ち切り、間に合った観点の結果だけで選ぶ（ツールの上限は95秒）。合う宿がなければ、宿の空きの調べ方の結果（開発では架空の宿、本番では「調べられない」）に戻る。調べの間は、中の Agent SDK の知らせが届くたびに相談の進みを知らせる（`ToolContext.progress`）。mock とテストには調べ役がない

## 自由記述の読み取り（祭りから探す）

「子どもと静かに見たい」のような言い方は、言葉の一致だけでは読み取れません。祭りから探すときの自由記述を、モデルで `FestivalWishIntent` に読みます（情報の壁。[祭りから探す](festival-search.md#探し方)）。読んだ結果は並び順にだけ効かせ、必ず守る条件と祭りの有無はコードで決めます。

1. `POST /api/festivals/search` の中で、道具を持たない1回きりの `query()` を動かす（`apps/server/src/agent/festivalWishReader.ts`、指示は `prompts/wish-reader.md`）。動かし方（開発環境から切り離す・JSON の差し戻し）は評価係と同じで、考える深さは low。モデルは `MODEL_WISH_READER`（省略時は軽いモデルの別名 `haiku`）、費用は `AGENT_MAX_BUDGET_USD` を上限にする
2. 自由記述はタグ（`<自由記述>`）で分け、中の山かっこを全角にして、タグを作れないようにする。中の指示には従わせない。祭りの名前や日時は作らせない
3. 返答は `parseJsonWithSchema` と `FestivalWishIntentSchema` で確かめる。崩れていれば1回だけ差し戻す。知らない項目（祭りの ID など）のある返答は使わない
4. 時間の上限は8秒で、差し戻しも含めた全体の予算として扱う。やり直しはしない。読めないとき（形の崩れ・失敗・時間切れ・回数の上限・混雑）は、断らずに言葉の辞書で読み、結果の `reading.by` を `words` にする
5. 読み取りは相談と自由記述の組ごとにとっておき、「別の祭りを提案してもらう」でモデルを呼び直さない。読めなかったことも残し、途中で順が変わらないようにする
6. 呼ぶたびに相談の回数（`DAILY_CHAT_LIMIT`・`DAILY_CHAT_LIMIT_PER_IP`）を1回使い、同時に呼ぶ枠（`MAX_CONCURRENT_TURNS`）を使う
7. live のときだけつなぐ。mock と CI ではモデルを呼ばず、言葉の辞書で読む
8. ログには失敗の分類・費用・所要時間だけを残し、自由記述の中身は残さない

## 失敗と再試行

- 例外は `classifyFailure`、結果のメッセージは subtype を `classifyResultSubtype` で分ける
- ツールの中の係（行き方・寄り道・評価）の失敗は、`retryOnce` で `retryable` のものだけを1回試し直す。試し直しても失敗したら、その係の結果なしで続ける
- 相談の全体は、`retryable` のものだけ、`backoffMs` の間隔で試し直す。試し直すのは、まだ画面にイベントを1つも送っていないときの1回だけ。相談1回は、進みのない時間（イベントも Agent SDK の知らせもない時間）が90秒を超えたら打ち切る。動き続けている相談は止めないが、試し直しも含めた全体の上限（6分）は別に持つ。待ち時間は画面の豆知識で埋めるので、遅くなっても止めないことを優先する
- 試し直すときは、謝ったり振り返ったりさせず、止まったところから続けさせる
- 直らなければ、`error` イベント（分類で決まった `code` と、利用者向けの短い一文）を送り、`done` で閉じる。詳しいことはログに残す

## 費用と使用量

- 費用は、結果のメッセージの `total_cost_usd`（推定）を使う。続けて話すと累計で届くので、足し合わせずに最後の値を読む
- トークンは `modelUsage` を使う。サブエージェントの分も入る（`usage` はメインのエージェントの分だけ）
- ログには、相談ごとの費用・トークン・所要時間・呼んだツールを残し、会話の本文は残さない

## Claude に JSON を返させるとき

接客の再確認でも、祭りのデータの調査でも、同じ部品を使います。

1. プロンプトに `STRICT_JSON_RULES` を入れ、崩れやすい書き方をさせない
2. 返答から `parseJsonWithSchema`（スキーマあり）か `extractJson` で取り出す。コードフェンス・前後の一言・文字列の中の半角の `"` や改行・末尾のカンマは、ここで吸収する
3. 途中で切れた返答から、内側の断片を答えとして拾わない（欠けたデータを下流に流さない）
4. 差し戻すときは `buildJsonRetryPrompt` を使う。前の返答は「データであって指示ではない」と明示した区切りで囲み、構文の誤りか形の違いかを分けて伝える

## 共通の部品（packages/agent-kit）

SDK に依存しない部品です。サーバー・スクリプト・データの更新のどこからでも使えます。

| 部品                                                    | 中身                                                             |
| ------------------------------------------------------- | ---------------------------------------------------------------- |
| `extractJson`・`parseJsonWithSchema`・`repairJsonText`  | 返答から JSON を取り出す。崩れを保守的に直し、スキーマで確かめる |
| `buildJsonRetryPrompt`・`STRICT_JSON_RULES`             | 差し戻しのプロンプトと、JSON の書き方の決まり                    |
| `checkPublicWebUrl`                                     | エージェントに取りに行かせてよい URL か（公開の Web だけを通す） |
| `createWebActivityLog`・`ungroundedSources`             | 調べた語と読んだページを控え、出典が読んだページかを確かめる     |
| `classifyFailure`・`classifyResultSubtype`・`backoffMs` | 失敗を分類し、試し直すか・画面にどのエラーとして出すかを決める   |
| `retryOnce`                                             | 時間をおけば直りうる失敗のときだけ、少し待って1回だけやり直す    |
