# 旅のガイドの仕様

しおりを受け取ったあとも、専属のガイドが旅の終わりまで付き添います。旅のことをいつでも相談でき、留守の間の変化は見回りで見つけて知らせ、組み直しを提案します。型は `packages/schema` の `guide.ts` にあります。

取り除く壁は次の3つです。

| 壁   | ガイドがすること                                               |
| ---- | -------------------------------------------------------------- |
| 情報 | 開催の変更や中止を、出典と調べた時刻を添えて知らせる           |
| 作法 | 出発の前にも当日にも、その旅の祭りの作法を答える               |
| 計画 | 変化や当日の遅れに合わせて、組み直しを提案する。承認すると直る |

## 旅の時期ごとの動き

時期は旅程の日付と今日からコードで決めます（`tripPhase`）。

| 時期（`TripPhase`） | いつ           | ガイド                                                     | 見回り                                     |
| ------------------- | -------------- | ---------------------------------------------------------- | ------------------------------------------ |
| `before`            | 初日より前     | 持ち物・作法・雨のときの案・行き方を答える。変化を知らせる | 頼まれていれば動く                         |
| `during`            | 初日から最終日 | 遅れ・迷子・忘れ物・体調の相談を受け、残りの予定を提案する | 頼まれていれば動く                         |
| `after`             | 最終日より後   | 付き添いを終え、旅のデータを消す案内をする                 | 止める（最終日の翌日 `endsOn` に `ended`） |

## 話せること・できないこと

| 話せること                                         | できないこと               |
| -------------------------------------------------- | -------------------------- |
| その旅の移動・宿・食事・持ち物・雨のときの案・作法 | 予約・支払い・外部への送信 |
| 祭りのない日の過ごし方                             | 承認なしの旅程の変更       |
| 当日の遅れ・迷子・忘れ物                           | 体調や事故の診断と判断     |
| 旅程を直す提案（承認すると新しい版になる）         | 他の人の旅についての相談   |

- 分からないことは推測で答えず、調べるか、分からないと言う。調べて答えたら、出典と調べた時刻を添える（`guide.sources`）。出典はツールの結果からコードが決め、モデルには書かせない。この発言で調べた Web と通知の出典を先に、8件まで添える。保存してある祭りのデータの出典には、今の時刻ではなく出典自身の確認した日を使う
- 体調や事故など緊急のときは、診断も判断もせず、公的な連絡先（`EMERGENCY_CONTACTS`：119・110）を返答の文より先に出す（`guide.emergency`）。コードが発言の言葉で見分け、モデルを待たずに送る（`apps/server/src/guide/emergency.ts`）
- 緊急の言葉は本文の形を確かめた直後に見分け、保存の口を待たずに SSE を開いて連絡先を先に送る。相談と旅はそのあとで開く。保存の口が止まったら、待つのは5秒までで、決まった文と案内で閉じる
- 1日の上限・混雑・前の返事の途中・モデルの失敗・時間切れ、相談の期限切れ・旅がない・保存の口の失敗でも断らず、連絡先と決まった文を返す。そのあとに、ふつうの発言と同じ案内（新しく始める、もう一度送る、また明日など。`error`）も添える。緊急の言葉がたまたま当たった発言でも、案内を失わないように
- 見逃しの害のほうが大きいので、言葉は広く取る（けが・具合が悪い・苦しい・助けて・死にたい など。かな書きと英語も）。ただし当たると、連絡先のほかに、続きの要約の話題に `trouble` が付き、返事を作れないときは決まった文が流れ、モックでは緊急の案内の記録が流れる。そこで、ふつうの相談に出る言い方（預けられますか・計画を立てます・歴史を意識した・堅苦しくない・help me plan・fire festival など）には当てないよう、紛らわしい言葉は形で見る

## 3つの役の権限

Web を読む役に利用者の情報を持たせず、利用者の情報を持つ役に Web を読ませません。ページに悪い指示が書かれていても、利用者の情報に届かないようにするためです。間はモデルを使わないコードの検問でつなぎます。動かし方は [接客エージェントの実行の仕様](agent-runtime.md#ガイドの3つの役) にあります。

例外として、ガイドのツールの中の1回きりの調べ役には、調べるのに要る項目だけを渡します。ページの指示で外へ送らされても、この項目のほかには届きません。利用者の名前と ID、旅の ID、連絡先、手帳、現在地の座標は渡しません。

| 調べ役                     | 渡す項目                                                                                                      |
| -------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Web（`research_web`）      | ガイドが書いた質問だけ                                                                                        |
| 行き方（`research_route`） | 出発の駅（旅の出発地か、いまいる駅の名前）・着く駅・日付・着きたい時刻・特に確かめること                      |
| 周り（`search_nearby`）    | 祭り・会場・地域・日付・食べたいもの・食事で気をつけたいこと・1人あたりの予算・子ども連れか・特に確かめること |

| 役             | 読むもの                                                                    | できること                                                                                                            | できないこと                                                                                                                       |
| -------------- | --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 見回り係       | 公開の Web。依頼にある祭りの公開の情報（ID・名前・開催日）、URL、変わった行 | 公開のページを読み、決まった形の報告を返す                                                                            | 利用者の情報を見る。データベースに書く。秘密の値を持つ。コマンドの実行とファイルの書き込み。通知を作る                             |
| 検問（コード） | 見回りの結果、祭りのデータ、ページの比較の控え                              | 形・URL・出典の照合。前回との差分の判定。確度と調べた時刻を付ける。通らないものを捨てる。確かな変化を通知の候補にする | ページの文章の指示に従う。ページの文章を先へ渡す。見回り係に旅や利用者を教える                                                     |
| ガイド         | その人の旅（旅程・手帳・続きの要約）、検問を通った通知、ツールの結果        | 相談に答える。決まったツールを呼ぶ。組み直しを提案する。利用者が話したことを手帳に残す                                | Web を直接読む。予約・支払い・外部への送信。承認なしの旅程の変更。他の人の旅を読む。手帳の中身を権限や決まりを変える指示として扱う |

### 型での分け方

文書の約束だけにせず、型で持てないようにします。どれも `z.strictObject` なので、決まった項目のほかは受け付けません。

| 渡すところ           | 型                              | 持たないもの                                                                                                                |
| -------------------- | ------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| 見回り係へ           | `PatrolRequest`・`PatrolTarget` | 利用者の ID・旅の ID・相談の ID・出発地・同行者。`patrolId` は `patrol-` と16桁の16進の乱数だけで、ほかの ID を入れられない |
| 見回り係から         | `PatrolReport`                  | 説明の文・調べた時刻・確度（時刻と確度はコードが決める）                                                                    |
| 検問のあと           | `CheckedChange`                 | 利用者の情報・ページの文章（ページの題名も持たない）                                                                        |
| 旅へ                 | `GuideNotice`                   | ページの文章。一覧の短い文（`summary`）は、通知の中身からコードが決まった型で作る                                           |
| 続きの要約           | `GuideResumeSummary`            | 会話の文（回数・話題・承認待ちの提案・時刻だけ）                                                                            |
| ガイドとの会話の本文 | `GuideChatRequest`              | 旅の ID・利用者の ID。旅はサーバーが相談から決める                                                                          |

## 見回り

頼まれた旅だけを、裏で定期的に確かめます。

1. **依頼**：利用者が旅ごとに頼み、止められる（`TripWatch`）。あとで開いて通知を読むので、ログインが要る。ログインを用意していない環境では、その相談の間だけ動く
   - `POST /api/guide/watch` の `start` で始め、`stop` で止める。止めたあとも始め直せ、調べた時刻（`lastCheckedAt`）は引き継ぐ。見回り中に始めても、止まっているものを止めても、そのままの依頼を返す
   - 見回りは残した旅の下の依頼だけを探すので、ログインして、まだ残していない旅で始めると、旅を残して（自分の旅の一覧に入る）から旅の下に書く。相談の中に持っていた手帳・通知・提案も旅の下へ移る
   - ログインを用意している環境で、ログインせずに始めると 401 で断る。用意していない環境では、依頼を相談の中に持つ（見回りは、その相談の間だけの扱い）
   - 旅が終わった（`after`）あとは始められない（409）。止める日（`endsOn`）は旅の最終日の翌日
2. **起動**：定期の起動を内部の API で受け、頼まれた旅から祭りと開催日を集める。同じ祭りを複数の旅で見張っていても、調べるのは1回
3. **比較**：コードが公開のページを取得し、行に分けて前回と比べる。変化がなければモデルを呼ばず、調べた時刻だけを残す。相対的な時刻（「3日前」など）だけの変化は無視し、日付・時刻・数字の変化は更新として扱う
4. **見回り係**：変わったページと、コードで読めないページだけを `PatrolRequest` にして渡す。対象の URL は開始の発言に入れる
5. **検問**：報告を `PatrolReportSchema` で確かめ、読んだ URL と出典を照らし合わせる。開催の日時は前回の値とコードで比べ、変化の種類を決める。写した開催日の文（`dateText`）は照合だけに使って捨てる
6. **配布**：検問を通った変化（`CheckedChange`）を、影響する旅の通知（`GuideNotice`）にする。確かめ切れないものは、値を持たないお知らせにする

宿の空きは、モデルを使わず今の処理をコードで呼びます。結果は同じ `CheckedChange` の形にします。天気の変化はまだ見回りません。見回りが動くのは live で鍵があるときだけです。取得・検問・失敗の扱いの決まりは [旅の見回り](operations.md#旅の見回り) にあります。

## 通知

| 種類（`content.kind`） | 中身                       | 提灯を灯す屋台（`noticeStall`） |
| ---------------------- | -------------------------- | ------------------------------- |
| `schedule_change`      | 開催の日・開始・終了の変更 | 本部のテント                    |
| `cancellation`         | 中止                       | 本部のテント                    |
| `announcement`         | 主催者のお知らせの種類     | お知らせの種類で決める          |
| `availability`         | 宿の空き                   | 宿                              |
| `weather`              | 雨・荒天・暑さ             | 天気                            |

- すべての通知に、出典（1つ以上）と調べた時刻（`checkedAt`）がある。どちらも欠けた通知は型で作れない
- 推定の出典は使えない。中止と日程の変更は、公式か、2つ以上の情報源で一致したときだけ知らせる
- 同じ変化から通知を2度作らない（`fingerprint`）。1つの旅の通知は `MAX_NOTICES_PER_TRIP` 件まで
- 影響する予定だけに絞り（`affectedItemIds`）、ガイドが利用者の言葉で短く説明する。説明に使うのは通知の値だけ
- 次に開いたときに届ける。アプリの外への通知はここに含まない
- 読んだら `POST /api/guide/notices/read` で知らせる。この旅の通知だけを読んだことにし（`readAt`）、ほかの ID は、ないものとして扱う。この旅の通知が1つもなければ 404。応答の未読の数は、上限で押し出された通知を除いた、保存の口の数
- 画面の未読の数と提灯は、サーバーの数に合わせる。見回りが上限に達して古い通知を押し出すと、画面の手元の数と合わなくなるので、返答の終わり（`guide.done`）や既読の応答の未読の数が手元と違えば、`POST /api/guide/state` で読み直す

お知らせの種類（`NoticeTopic`）と屋台の組み合わせは、`traffic` 行き方、`reception` 作法、`rain` 天気、`venue`・`program`・`other` 本部のテントです。お知らせの文章は持たないので、くわしくは出典のページを開いて読みます。

## 組み直しの提案

提案は、承認されるまで旅程を変えません。

- 影響する予定だけを直した案を、今の旅程の検証と評価に通してから見せる。通らない案は見せず、通知だけを届ける
- 提案は、元の版（`baseVersion`）・内容のハッシュ（`contentHash`：提案した旅程の JSON の SHA-256）・期限（`expiresAt`）を持つ
- 承認のときは版とハッシュを照らし合わせる。提案のあとに旅程が変わっていたら適用せず（`stale`）、期限を過ぎていたら適用せず（`expired`）、作り直しを案内する
- 同じ承認が2回届いても、同じ結果を返し、版は1つしか増えない
- 適用できたか確かめられないときは自動でやり直さず、いまの版を見せる（`unknown`）
- 断ると旅程は変わらない。同じ変化から提案を重ねて作らない
- 承認を待てる提案は1つの旅に `MAX_PENDING_PROPOSALS` 件まで。上限に達したら新しい提案を作らず、先に決めてもらうよう案内する
- 期限（`expiresAt`）は作ってから3日か、旅の最後の日の終わりの、早いほう。承認を待てるのは、状態が `pending` で、元の版が今の版と同じで、期限の前の提案だけ
- ガイドが書くのは、影響する予定だけの直し（`propose_change` の `edits`：時刻を変える・外す・置き換える・足す、その日の泊まり・帰りの最終・食事の案を直す）。コードが今の旅程に当て、`update_itinerary` と同じ検証に通す。旅の日を増やしたり減らしたりする変更はガイドでは提案しない
- 評価は、基準に届いているか、今の旅程より悪くならない案を通す（今の旅程がもともと基準に届いていないときに、直せる案まで止めないため）
- ガイドは調べた場所の採否を書かない。前の版の採否は引き継ぎ、この相談で調べて案に入れなかった場所の理由はコードが補う（周りを探しただけで、直しと関係なく評価が下がらないように）
- 今の旅程と同じ計画（予定・泊まり・食事の案・帰りの最終が同じ）の案は作らない。帰りの最終だけの直しは、予定の差分が空でも案にする
- 通知への案（`noticeIds`）では、通知の開催の変更を祭りのデータに重ねて照らす。祭りのデータの更新は週に1回なので、新しい時刻の案が今のデータで断られないようにする。重ねるのは検問を通った通知の値だけ
- `POST /api/guide/state` は承認待ちの提案だけを返す（提案は旅程をまるごと持つので、応答を大きくしない）。通知の `proposalId` の提案が一覧になければ、もう決まったか無効になった提案として扱い、作り直しを案内する
- 承認したあとでも前の版に戻せる。戻す操作も新しい版として残し、差分を見せる（`POST /api/guide/revert`）

承認・却下・戻すの決まり（`apps/server/src/guide/decision.ts`、`POST /api/guide/proposals/:id/decision`）は次のとおりです。

| 場面                                    | 応答                                                                                              |
| --------------------------------------- | ------------------------------------------------------------------------------------------------- |
| 版とハッシュが合い、期限の前            | `applied`。提案の旅程を新しい版として保存し、保存の口から読み直して確かめてから、提案を承認にする |
| もう承認した提案（同じ承認が2回届いた） | `applied`。当て直さず、同じ新しい版と差分を返す                                                   |
| 当てたあとに提案の状態を書けなかった    | `applied`。今の旅程がその提案の版とハッシュなら、当ててあるとみなして承認にする                   |
| 見た提案と版かハッシュが違う            | `stale`。提案の状態は変えない（画面に古い提案が残っていた）                                       |
| 提案のあとに旅程が変わった              | `stale`。提案を `stale` にする                                                                    |
| 期限を過ぎた                            | `expired`。提案を `expired` にする                                                                |
| 断った提案                              | `rejected`                                                                                        |
| 保存したか確かめられない                | `unknown`。自動でやり直さず、読めたときは今の版を返す                                             |
| ほかの人の提案・ない提案                | 404（あるかどうかを見せない）                                                                     |

- 同じ旅の承認と戻す操作は、インスタンスの中で1つずつ行う。2つの承認が同時に届いても、2つ目は1つ目の結果を見てから決めるので、版は1つしか増えない
- 断る（`reject`）と、提案を `rejected` にし、旅程は変えない。もう承認した提案は断れない（409。前の版に戻してもらう）
- 戻すときは、今より前の版を選ぶ（今の版かそれより後は 409、残っていない版は 404、今の旅程と同じ計画なら 409）。前の版の中身を次の版として残し、差分と予定ごとの「最後に変わった版」は今の旅程から計算し直す。保存したか確かめられないときは、自動でやり直さず 503 で旅程を読み直してもらう。戻すと、承認待ちの提案は元の版が今の版と違うので、承認できなくなる
- 前の版は、ログインしている人は自分の旅程から、ログインしていない相談は持ち主のない旅程から読む（旅程の版は20まで残る）

## ガイドの手帳

同行者の好み、歩くペース、避けたいことなど、その旅に役立つことを短い項目で残します（`GuideMemoItem`。1項目 `MAX_MEMO_TEXT_LENGTH` 字、`MAX_MEMO_ITEMS` 件まで）。

- 旅ごとに持ち、別の旅や他の人には見せない。残すのは利用者が話したことだけで、Web のページや見回りの結果から書き足さない
- 利用者が話したことかは、コードで照らす。`save_memo` は発言をそのまま写した部分（`quote`）を受け取り、それがこの発言の中にあり、残す文のほとんどの言葉が発言の中にあり、発言にない文字が長く続かないときだけ残す（発言に指示を混ぜた文は通らない）。発言の本文はサーバーが持ち、モデルの入力からは受け取らない
- 項目を残すときは利用者に知らせる（`guide.memo`）。利用者は一覧で見て、直して、消せる
- 現在地、体調の詳しい内容、連絡先、秘密の値は残さない。残さない文かはコードが言葉で確かめ（`apps/server/src/guide/memo.ts`）、利用者が直すときも同じものを断る。見分けられないものは残さないほうへ倒す
- 手帳の中身は参考の情報として扱う

## データの保存と消し方

| 残すもの                                                                                     | 置き場                                       | 消える時期                                                                 |
| -------------------------------------------------------------------------------------------- | -------------------------------------------- | -------------------------------------------------------------------------- |
| ガイドの1日の使った量（回数と費用の見積もり）                                                | `users/{uid}/guideUsage/{日}`                | 3日で消える                                                                |
| 見回りの依頼                                                                                 | `users/{uid}/trips/{旅の ID}/watch/current`  | 旅を消すとき。旅が終わると止まる                                           |
| 通知                                                                                         | `users/{uid}/trips/{旅の ID}/notices/{ID}`   | 旅を消すとき。旅の最終日から30日                                           |
| 提案                                                                                         | `users/{uid}/trips/{旅の ID}/proposals/{ID}` | 旅を消すとき。旅の最終日から30日                                           |
| 手帳                                                                                         | `users/{uid}/trips/{旅の ID}/memo/{ID}`      | 旅を消すとき                                                               |
| 続きの要約                                                                                   | 相談の途中の状態（`sessions/{相談の ID}`）   | 相談と同じ（最後に使ってから6時間）                                        |
| ページの比較の控え（行のハッシュ・調べた時刻・実行権・検問を通った開催の日時・届け直す変化） | `patrols/{祭りの ID}_{開催日}`               | 見回る旅がなくなったとき。利用者の情報を持たず、ページの文章もコピーしない |
| 見回りの実行の記録（調べた祭りと URL・分類ごとの数・費用）                                   | `patrolRuns/{見回りの ID}`                   | 30日で消える。利用者の情報とページの文章を持たない                         |
| Webhook の配信の受け取りの印                                                                 | `patrolDeliveries/{配信の ID}`               | 7日で消える                                                                |

残さないものは次のとおりです。

- 会話の全文（Agent SDK の会話の記録はインスタンスの一時ディレクトリにだけ置き、保存先やログに出さない。別のインスタンスに届いた相談は、コードが書く短い要約 `GuideResumeSummary` と旅の要約から新しい会話で続ける）
- 現在地（その発言のときだけ使う。ログにも残さない。入れた発言の会話の記録は消し、次の発言は要約から新しい会話で続ける）
- 検問で捨てたもの（ページの行・写した開催日の文・見回り係の見立て）

ログには分類・件数・費用・所要時間だけを残し、発言の本文・現在地・手帳の中身を残しません。

旅の下（`users/{uid}/trips/{旅の ID}/…`）に置くのは、残した旅のデータだけです。旅を消すと、旅の下をまるごと消すので、手帳・通知・提案・見回りの依頼がいっしょに消えます。読み書きは `storage.forOwner(持ち主).tripDocs(旅)` の口だけで行います。読むときに呼ぶ側でスキーマを通し、期限を過ぎた文書は TTL で消える前でも読みません。

| 種類               | 文書の形                                                                                                                  |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| 見回りの依頼・通知 | 項目を平らに置き、`expiresAt` を足す。見回りが頼まれた旅を `status` で探せるように（`collectionGroup("watch")`）          |
| 手帳・提案         | `{ json, updatedAt, expiresAt }`。提案は旅程をまるごと持ち、自分の期限の項目（`expiresAt`）もあるので JSON の文字列にする |

保存先がメモリのとき（手元の開発）は、見回りもガイドと同じメモリの置き場で依頼と旅程を読み、通知を書きます（`MemoryTripStorage.patrolTrips`）。Firestore で `collectionGroup("watch")` を読むのと同じ役で、利用者の操作からは呼びません。

ログインせずに使っているとき（残す前の旅も同じ）は、手帳と通知と提案はその相談の間だけ持ちます（`sessions/{相談の ID}` の `guide`）。ログインして旅を残すと、次に開いたときに旅の下へ移します。旅が消されると、相談の中に持っていたものも消します。消すのは保存の口が「ない」と答えたときだけで、読み取りの一時的な失敗や読めない形の旅程では消しません。

## API

旅は相談から決めるので、本文に旅の ID や利用者の ID を持ちません。相談の ID を URL に載せず本文で送るのは、ログインなしの相談では、相談の ID を知っていれば読めるからです。他の人の相談・通知・提案は、あるかどうかも見せず 404 にします。

live でガイドのモデル（`MODEL_GUIDE`）を設定していないときは、ガイドの入口だけが 404 で断ります（`ガイドは用意していません`）。サーバーは起動し、今の相談は動きます。相談に旅程がまだないときは 409、旅が消されているか読めない形のときは 404、保存の口が一時的に失敗して手元の写しもないときは 503（もう一度送れる）です。

緊急の言葉がある `POST /api/guide/chat` は、相談がない・ほかの人の相談・旅程がない・旅が消された・保存の口の失敗のときも、4xx や 5xx の代わりに 200 の SSE で、連絡先（`guide.emergency`）、決まった文（`message.delta`）、ふつうの発言と同じ案内（`error`）、`guide.done` の順に返します。相談の中身を読まないので、ない相談とほかの人の相談は同じ応答で、`guide.done` の数は0、時期は `during` です。

| メソッド | パス                                | 決まり              | 本文                             | 返すもの                                                                                         |
| -------- | ----------------------------------- | ------------------- | -------------------------------- | ------------------------------------------------------------------------------------------------ |
| POST     | `/api/guide/open`                   | ログインした持ち主  | `GuideOpenRequestSchema`         | 201 `SessionResponseSchema`。残した旅を開いて、ガイドと話す相談を作る                            |
| POST     | `/api/guide/state`                  | 相談の持ち主        | `GuideSessionRefSchema`          | `GuideStateResponseSchema`（時期・見回り・通知・承認待ちの提案・手帳）                           |
| POST     | `/api/guide/chat`                   | 相談の持ち主        | `GuideChatRequestSchema`         | 返答を SSE（`GuideSseEventSchema`）で返す                                                        |
| POST     | `/api/guide/notices/read`           | 相談の持ち主        | `MarkNoticesReadRequestSchema`   | `MarkNoticesReadResponseSchema`（未読の数）                                                      |
| POST     | `/api/guide/watch`                  | 相談の持ち主        | `SetTripWatchRequestSchema`      | `TripWatchSchema`。始めるときはログインが要る（用意している環境だけ）                            |
| POST     | `/api/guide/proposals/:id/decision` | 相談の持ち主        | `DecideProposalRequestSchema`    | `DecideProposalResponseSchema`                                                                   |
| POST     | `/api/guide/revert`                 | 相談の持ち主        | `RevertTripRequestSchema`        | `TripChangeSchema`（新しい版の旅程と差分）                                                       |
| POST     | `/api/guide/memo/:id`               | 相談の持ち主        | `UpdateGuideMemoRequestSchema`   | `GuideMemoItemSchema`                                                                            |
| POST     | `/api/guide/memo/:id/delete`        | 相談の持ち主        | `GuideSessionRefSchema`          | 204                                                                                              |
| POST     | `/internal/patrol/start`            | 内部（`oidc`）      | なし                             | 調べた対象の数・見回り係に渡した数など（`PatrolTickResult`）。見回りを動かしていない環境では 404 |
| POST     | `/internal/patrol/webhook`          | 内部（`signature`） | Managed Agents の Webhook の本文 | 204。見回りを動かしていない環境では 404                                                          |

内部の経路は `routes.internal` で足し、呼び出し元の確かめは [内部の入口](api.md#内部の入口) の検証（`oidc`・`signature`）だけで行います。確かめられなければ 401、検証の設定がなければその入口だけ 404 で、ハンドラーには届きません。

断るときの応答は [API の仕様](api.md#断るときの応答) と同じ `ApiErrorSchema` です。

## SSE イベント

店内の相談（`SseEventSchema`）とは別の接続で流します。形は `GuideSseEventSchema` で、送る前（`encodeGuideSseEvent`）と受け取ったあと（`decodeGuideSseEvent`）にスキーマで確かめます。画面は `apps/web/src/state/` でストアの更新に変えます。

| イベント           | いつ                     | 主な中身                               |
| ------------------ | ------------------------ | -------------------------------------- |
| `guide.tool.start` | ツールを呼ぶ前           | 呼び出し ID、ツール名、吹き出し        |
| `guide.tool.end`   | ツールが終わった         | 成否、吹き出し                         |
| `guide.emergency`  | 緊急の相談               | 公的な連絡先。返答の文より先に送る     |
| `guide.notice`     | 会話の中で通知を知らせた | 通知                                   |
| `guide.proposal`   | 組み直しの提案ができた   | 提案。旅程はまだ変わっていない         |
| `guide.memo`       | 手帳に項目を残した       | 手帳の項目                             |
| `message.delta`    | ガイドの返答の続き       | 店内の相談と同じ形                     |
| `guide.sources`    | 返答に添える出典         | 返答の ID、出典（1つ以上）、調べた時刻 |
| `error`            | うまくいかなかった       | 店内の相談と同じ形                     |
| `guide.done`       | 返答の終わり             | 旅の時期、未読の通知の数、承認待ちの数 |

1つの発言に1本の接続を使い、最後に必ず `guide.done` を送って閉じます。接続が切れても自動で再接続しません。吹き出しの文章は、サーバーが決まった型から作ります。

## ガイドのツール

入力に旅の ID や利用者の ID を持たせず、サーバーの文脈から決めます。モデルに ID を書かせないので、他の人の旅についての呼び出しを作れません。

| ツール（`GUIDE_TOOL_NAMES`） | すること                                                                    |
| ---------------------------- | --------------------------------------------------------------------------- |
| `read_trip`                  | その人の旅程を読む                                                          |
| `list_notices`               | 検問を通った、その旅の通知を読む                                            |
| `research_web`               | Web を読む1回きりの調べ役をツールの中で動かし、確かめた結果と出典だけを返す |
| `get_weather`                | 天気を調べる（店内の相談と同じ処理）                                        |
| `research_route`             | 行き方を調べる（店内の相談と同じ処理）                                      |
| `search_nearby`              | 周りの店や寄り道を調べる（店内の相談と同じ処理）                            |
| `propose_change`             | 組み直しの提案を作る。旅程は変えない                                        |
| `save_memo`                  | 利用者が話したことを手帳に残す                                              |

## 失敗の扱い

| 場面                                 | 動き                                                                                                                                                                       |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 見回り係が失敗した・報告が崩れていた | 通知を作らず、次の回に調べ直す。失敗が続くページは間隔を空ける                                                                                                             |
| 値がページで確かめられなかった       | 捨てて、分類だけをログに残す。開催に関わる語が新しい行にあるときは、公式か確かな出典のページなら値を持たないお知らせにする。本物の中止を黙って失わないため                 |
| 定期の起動や Webhook が2回届いた     | 実行権と ID で重複を除き、同じ作業を二重に走らせない                                                                                                                       |
| 署名の鍵や検証の設定がない           | その入口だけ 404 で断る。設定がないから通す、という動きにしない                                                                                                            |
| 組み直しの案が検証を通らなかった     | 案を見せず、通知だけを届ける                                                                                                                                               |
| 承認のときに版かハッシュが違う       | `stale`。適用せず、作り直しを案内する                                                                                                                                      |
| 適用できたか確かめられない           | `unknown`。自動でやり直さず、いまの版を見せる                                                                                                                              |
| ガイドの返事を作れなかった           | `error` のあと `guide.done` で閉じる。分類は [接客エージェントの実行の仕様](agent-runtime.md#失敗と再試行) と同じ。緊急の発言は、連絡先と決まった文のあとに `error` を送る |
| 回数や費用の上限に達した             | `rate_limited`（429）で断る。上限は利用者と旅ごとに持つ（下の「費用と回数の上限」）。緊急の発言は断らず、連絡先と決まった文のあとに `error` で知らせる                     |

## 費用と回数の上限

1日の回数と費用（Agent SDK の推定）を、利用者ごとと旅ごとに数えます（`apps/server/src/guide/limits.ts`）。

| 上限           | 環境変数                        | 設定がないとき |
| -------------- | ------------------------------- | -------------- |
| 回数（利用者） | `GUIDE_DAILY_TURNS_PER_USER`    | 60             |
| 回数（旅）     | `GUIDE_DAILY_TURNS_PER_TRIP`    | 40             |
| 費用（利用者） | `GUIDE_DAILY_COST_USD_PER_USER` | 3 米ドル       |
| 費用（旅）     | `GUIDE_DAILY_COST_USD_PER_TRIP` | 2 米ドル       |

- ログインしている人の分は保存の口に残し、再起動やインスタンスの増減で数え直されないようにする。ログインしていない人の分は、そのインスタンスのメモリで IP ごとに数える
- 費用には、ツールの中の1回きりの調べ（Web・行き方・寄り道・評価）の分も含める。再開した会話の費用は累計で届くので、前の累計との差を数える。結果が届かなかった発言（切断・時間切れ・失敗）には、見積もりの最低額（2セント）を足す
- ツールの中の調べは、それぞれの上限（`AGENT_MAX_BUDGET_USD`）と今日の残りの小さいほうで抑える。残りがなければ呼ばない
- 1回の発言の費用の上限は、`AGENT_MAX_BUDGET_USD` と今日の残りの小さいほう
- 日ごとの費用の上限は、近くなると少し超えることがある。動いている会話の費用は結果が届くまで分からないので、その発言の本体と調べ、同時に進んでいる発言の分だけ超える
- 中断した調べ（切断や時間切れ）は費用が分からないので、最低額だけを数える。切り続ける使い方は、回数の上限で止める
- 店内の相談と同じ、全体と、IP ごとと利用者ごとの1日の回数の上限（`DAILY_CHAT_LIMIT`・`DAILY_CHAT_LIMIT_PER_IP`）と、同時に返事を作る数の上限（`MAX_CONCURRENT_TURNS`）も使う。超えた発言は 503 で断る
- ログインしている人の使った量は、利用者の分と IP の分の大きいほうで見る（登録し直しても上限を回避できない）。IP の分はメモリに持つ
- お試し用のアカウントは IP ごとに数え、回数は専用の全体の枠（`DAILY_TRIAL_CHAT_LIMIT`）で、費用は全員を合わせた上限（`GUIDE_DAILY_COST_USD_TRIAL_TOTAL`）で抑える。どちらもメモリに持つので、初期化のスクリプトでは戻らず、日付が変わるか再起動で戻る
- 保存の口から使った量を読めなくても相談は止めない（全体の上限は効いたまま）

## サンプル

`data/samples/guide/` に、架空の祭りのガイドの相談と見回りがあります（[サンプルの説明](../../data/samples/README.md)）。モックモードでは、これを再生して、見回りの結果から承認までをキーなしで確かめます。

- 発言が記録と同じならその返答を、緊急の言葉があれば緊急の案内の記録を、それ以外はまだ流していない次の記録を流す
- 記録の通知と提案は、相談の旅に置き換えて届ける。主役の祭りと旅の日が同じ旅にだけ届ける
- 旅の時期と提案の期限は、記録の「話した日」（`today`）で決める
- 既読・見回りの開始と停止・承認・却下・前の版に戻すは、記録を流さず、live と同じ経路と保存の口で動く。承認すると旅程が新しい版になり、しおりも新しい版で開ける
