# ADR 0005：ログインに Firebase Authentication、保存先に Firestore を使う

- 状態：採用

## 背景

旅程と相談は、接客サーバーのメモリにしかなかった。サーバーが再起動したり台数が増えたりすると、共有したしおりの URL が開けなくなり、相談の続きが別のインスタンスに届くと「相談が見つかりません」になる。旅の前にしおりを持って出かけてもらうには、しおりの URL が出かける日まで開けることが要る。

また、組んだ旅を「あとで開きたい」「家族と見比べたい」という使い方には、利用者ごとに旅を残す仕組みが要る。一方で、相談そのものは思い立ったときに気軽に始めてほしいので、ログインを入口の条件にはしない。

## 判断

- ログインは Firebase Authentication の Google でのログインにする。相談はログインなしで始められ、旅を残す・あとで開く・一覧する・共有する・消すのはログインしてから
- アプリの利用者のログインだけを扱う。Claude のアカウントでのログインは出さない
- 保存先は Firestore（ネイティブモード、`asia-northeast1`）。読み書きは接客サーバーだけが Admin SDK で行い、ブラウザからの読み書きはセキュリティルールですべて断る
- 利用者は、ブラウザが送る Firebase の ID トークンをサーバーで確かめて決める。ブラウザが送る利用者の ID は使わない
- 保存の口は interface にし、Firestore の実装とメモリの実装（テストと手元用）を同じテストで確かめる
- 旅程は版ごとに、丸ごと JSON の文字列で残す。読むときにスキーマを通し、いまの形で読めない古い版は「読めない」として扱う
- 消す時刻（`expiresAt`）を文書に持たせ、Firestore の TTL ポリシーで消す。持ち主のない旅程と共有は30日、相談の途中の状態は6時間
- 会話の全文は残さない。相談の途中の状態として残すのは、条件・こだわり・候補・選んだ祭り・旅程の ID・段階だけ

## 結果

- 良い点：しおりの URL がサーバーの再起動や台数に左右されない。どのインスタンスに届いても、相談の続きと旅程を読める。鍵のファイルを作らず、Cloud Run の実行用のサービスアカウントの権限（`roles/datastore.user`）だけで読み書きできる
- 引き受けること：
  - Agent SDK の会話の記録はインスタンスの `/tmp` にあるので、別のインスタンスに移った相談は、相談の状態の要約からエージェントが続ける（細かな言い回しは引き継がない）
  - 1日の相談の回数と同時に返事を作る数の上限は、まだインスタンスごとに数える。インスタンスの最大数を増やすと、上限もその数だけ増える
  - 旅程の形を変えたときは、古い版が読めなくなることがある。一覧の見出し（名前・初日）は保存のときに別に持つので、一覧には出続ける
  - ログインの記録（Google のアカウントの名前とメールアドレス）は Firebase Authentication に残る。利用者は画面から、旅といっしょに消せる
