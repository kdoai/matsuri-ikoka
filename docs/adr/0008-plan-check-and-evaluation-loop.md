# ADR 0008：旅程にそろうべきものを型とコードで確かめ、評価係の採点が届くまで調べ直して作り直す

- 状態：採用

## 背景

旅程係が組んだ旅程が「行きの電車 → 祭り → 寄り道1か所 → 帰りの電車」だけになることがあった。昼と夜のごはん、乗り換えの駅、駅から会場までの最後の移動、帰りの最終が抜け、周辺係が見つけた場所も旅程に入らないまま、出来を確かめずに使う人に出していた。使う人は、その旅程のままでは旅に出られない（計画の壁）。

原因は4つあった。

- 旅程の型に、乗り換え・食事・最後の移動・帰りの最終・調べた場所の採否を書く場所がなく、抜けても型の上で区別できなかった
- 点検（`planCheck`）は予定どうしの矛盾しか見ておらず、足りないものを見ていなかった
- 経路・食事・寄り道の調べを旅程係が順に呼ぶかどうかに任せていて、呼ばれなければ調べないまま組んでいた。周辺係の結果は文章でコンシェルジュを通って届くだけだった
- 出来を採点する仕組みがなく、足りなくてもそのまま保存して報告していた

## 調べたこと

公開されている旅行計画の研究と、エージェントの設計の手引きを読んだ（2026-11-04 に確認）。

- 旅行計画のベンチマーク TravelPlanner は、計画を「環境・常識・利用者の条件」の3種類の制約で評価する。常識の制約には、調べた情報だけを使っているか（Within Sandbox）と、必要な情報が欠けていないか（Complete Information）が入っている。評価は決まったスクリプトで行い、モデルには採点させていない。また、エージェントの失敗の多くは、道具で調べる回数が足りず、足りないところを作り話で埋めたり省いたりすることで起きており、旅が長くなるほど悪くなると報告している（[論文](https://arxiv.org/abs/2402.01622)、[プロジェクトのページ](https://osu-nlp-group.github.io/TravelPlanner/)）
- 同じベンチマークで、計画・フィードバック・修正をくり返す枠組みを試した研究は、モデルが長い計画を読んで出すフィードバックは正確でないことが多く、修正が効かない場合があると報告している（[論文](https://arxiv.org/abs/2408.06318)）
- 旅程の条件を形式的な検査（SMT ソルバー）に渡し、満たせない理由をモデルに返して直させる研究は、ベンチマークの成功率を大きく上げた（[論文](https://arxiv.org/abs/2404.11891)）。検査の結果を、どこが足りないかが分かる形で返すことが効いている
- Anthropic のエージェントの設計の手引きは、生成と評価を別の呼び出しに分けてくり返す型（evaluator-optimizer）を、評価の基準がはっきりしていて、くり返すと良くなるときに勧めている。独立した作業を並べて動かす型（parallelization）は、速さと、観点ごとに注意を向けるために使うとしている（[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)）
- Agent SDK のサブエージェントの定義では、役割ごとにモデルと考える深さ（`effort`）を指定でき、フックの `SubagentStop` で `decision: "block"` を返すとサブエージェントを止めずに続けさせられる（[Subagents in the SDK](https://code.claude.com/docs/en/agent-sdk/subagents)、[Hooks](https://code.claude.com/docs/en/hooks)）

## 判断

1. **そろうべきものを型で決める。** 移動ごとの出発・到着・役目（行き・最後の移動・寄り道・帰り）・乗り換えごとの区間と出典、日ごとの昼・夜の食事の案と帰りの最終、調べた場所の採否と理由、点検の不足（`gaps`）、評価（`evaluation`）を `packages/schema` に足す。古い版の旅程を読めるよう、どれも任意にし、そろっているかは点検で確かめる
2. **足りないかはコードで決める（点検）。** TravelPlanner と同じく、確かめられることは決まったコードで確かめる（`apps/server/src/domain/planCoverage.ts`）。分からないところは推測で埋めず不足に書き、出典のない帰りの最終や食事の案は使わない。採ったかどうかも、予定の `spotId` からコードで決める。帰りの最終に間に合わない旅程は、矛盾として保存しない
3. **点と合否はコードで決め、モデルの評価係は足りなさを名指しする役にとどめる。** 長い計画へのモデルのフィードバックは当てにならないことがあるので、点検の不足から出す点（網羅・具体さ・無理のなさ・出典）を土台にし、評価係（別のモデル・別の文脈の1回きりの `query()`、道具なし）の点は、低いほうを採る形でだけ合わせる。合否と、どの係に何を調べ直してもらうかは、コードで決める（`apps/server/src/domain/planEvaluation.ts`）。評価係が失敗しても、点検の点だけで続ける
4. **基準に届くまで調べ直して作り直す（上限つき）。** evaluator-optimizer の型に、検査の結果を名指しで返すやり方を合わせる。基準（どの観点も70点以上）に届かなければ、足りない観点と頼みの文を付けて、経路・周辺・宿の係に調べ直しを頼み、旅程係が作り直す。1回の相談で評価は3回まで。届かなければ、足りない点をそのまま使う人に伝える。旅程係が基準に届かないまま終えようとしたら、`SubagentStop` のフックで作り直しに戻す（戻す回数にも上限を置く）
5. **調べを並べて動かし、失敗は分類して1回だけやり直す。** 経路（行きと、帰りの最終まで）と食事・寄り道を `research_trip` で並べて調べる。係の失敗は `@matsuri-ikoka/agent-kit` で分類し、時間をおけば直りうるものだけを1回自動でやり直す。やり直しても失敗した係は名前を返し、推測で埋めない
6. **旅程を組む係と評価係には強いモデルを使えるようにする。** モデルは環境変数（`MODEL_PLANNER`・`MODEL_EVALUATOR`）で指定し、コードに書かない。旅程係の考える深さは medium にする

## 採らなかったもの

- **SMT ソルバーなどの形式的な検査に計画そのものを解かせる。** 成功率は高いが、祭りの旅は営業時間・屋台・混雑など、式にしにくい条件が多い。時刻の矛盾と足りなさはコードの点検で確かめられるので、ソルバーは足さない
- **モデルだけに採点させる。** 長い計画への指摘が不正確なことがあり、点が揺れる。合否をモデルの点だけで決めると、足りない旅程が通るおそれがある
- **回数の上限を置かないくり返し。** 費用と待ち時間が読めなくなる。手引きの例のように基準に届くまで回し続けず、上限で止めて正直に伝える

## 結果

- 旅程に、乗り換え・食事・最後の移動・帰りの最終と、その出典がそろう。そろわないときは不足として残り、使う人に伝わる
- 調べ直しと作り直しの分、旅程づくりの時間と費用が増える（評価係の呼び出しは1回の相談で3回まで、1回50秒で打ち切る）
- 画面としおりで、不足と評価をどう見せるかは、別に決める
