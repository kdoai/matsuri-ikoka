# ADR 0009：祭りの週次の調査を Managed Agents の定期実行で進め、API キーなしで回収する

- 状態：採用
- [ADR 0007](0007-festival-refresh-workflow.md) を置き換える。データの更新の認証については [ADR 0004](0004-authentication.md) の API キーの方針も置き換える

## 背景

ADR 0007 では、GitHub Actions が祭りごとにセッションを起動して接続を保っていた。この形には次の問題があった。

- 実行の長さが GitHub Actions の時間の上限と接続に左右される。調べる祭りが増えると、直列では上限を超える
- 長く使える API キーを Secret Manager に置く必要がある
- 調べる祭りの選び方に「最近調べた祭りを外す」規則がなく、244件のうち219件が対象になる一方で週に5件しか調べないので、開催の近い同じ祭りを選び続ける

祭りの公式サイトは小さな町や神社のものが多く、前もって列挙できない（いまの出典のサイトは 648）。Web の許可リストを前提にできない。

## 判断

- 調査は Managed Agents の中で完結させる。Scheduled Deployment で週に1回起動し、リードが Dynamic Workflows で調査員に祭りごとの調査を任せ、`found` の報告を確認役が見直し、Outcomes の採点役が基準で確かめる
- GitHub Actions は、モデルを使わない短い準備と回収だけを行う。日付の計算と検査はコードで行うという決まりと、Web を読むセッションに権限を渡さないためである
- 調査リストは、GitHub Actions が Memory Store に置き、セッションは読み取り専用で読む。受け口を公開せずに済み、セッションから調査の対象を変えられない
- 結果は、セッションが終わったあとに Files API で回収する。Webhook は使わない。公開の受け口を増やさないためである
- 認証は Workload Identity Federation にし、API キーを置かない。連携のルールは、このリポジトリの main の `update-festivals.yml` の `schedule` と `workflow_dispatch` だけを受け付け、専用のワークスペースの中でだけ使える
- 調べる祭りは、開催の近い順に、節目（開催の30日前・14日前・7日前）で選ぶ。確定した開催回は終わるまで調べない。結果はコードだけが書く台帳（`data/research-ledger.json`）に残す。選び方は [運用の仕様](../spec/operations.md#調べる祭りの選び方) にある
- 祭りのデータの正は Git のままにする（[ADR 0002](0002-festival-data-as-json-in-git.md)）。エージェントはデータベースにも GitHub にも書き込まない

### ページの中の指示への備え

許可リストの代わりに、ページに悪い指示があっても被害が出ない形にする。

- ページを読むエージェント（調査員・確認役）は書き込めない。書くエージェント（リード）はページを読まない
- コマンドの実行はどのエージェントにも許さない。セッションに秘密の値・GitHub の権限・個人情報を置かない
- 報告は決まった項目だけを受け取り、変えてよい項目をコードで限る
- コードが、実際に開いたページか、引用が本文にあるか、文字に指示が混ざっていないかを確かめる
- 祭りの中身が変わる PR は人がマージする

### ほかの案

| 案                                                        | 採らなかった理由                                                                                               |
| --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| GitHub Actions を使わず、公開の役も Managed Agents で行う | GitHub のトークンをセッションに預けることになる。コマンドの実行も要る。Web を読むチームと権限を近づけない      |
| 調査から PR までを1つのセッションで行う                   | Web を読むチームと push の権限が同じ場所に置かれる                                                             |
| エージェントが Firestore に直接書く                       | 検査と人の確認を飛ばして本番に出る。旅程などのデータと同じ場所に権限を持つ。履歴と取り消しを作り直すことになる |
| 祭りごとにセッションを起動する（ADR 0007）                | 上の背景のとおり                                                                                               |
| Memory Store に調査の学びを書かせる                       | 悪い指示が翌週以降まで残る。受け渡しの Store は、セッションから読み取り専用にする                              |

## 結果

- 良い点：実行が GitHub Actions の時間の上限に左右されず、長く使える鍵がなくなる。調査が乗っ取られても、GitHub とクラウドの側でできることがない。同じ祭りを何度も調べない
- 引き受けること：
  - 公式のセキュリティのガイドとの違いが2つある。出典のサイトを列挙できないのでネットワークと Web の道具を絞らない。見ている人がいない定期実行で止まらないよう、道具を確認なしで動かす（どちらも、コマンドの実行を許さず秘密の値を置かないことで補う）
  - 確定後の中止や延期は週次の調査では追わない。旅程を確定する前の再確認で補う
  - 連携のルールは Claude Console で作る。ワークフローのファイル名を変えるときはルールも直す
  - 祭りの中身が変わる PR は、当面すべて人がマージする
