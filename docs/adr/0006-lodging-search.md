# ADR 0006：宿の空きと料金を、楽天トラベルの空室検索 API から取る

- 状態：採用

## 背景

泊まりの旅では、泊まれる宿が空いているか、予算に収まるかが分からないと、旅程が手配の手前で止まってしまう。宿の名前や料金はモデルに作らせられない（出典のない情報になり、すぐに古くなる）。公開されている宿泊予約の API から、調べた時刻つきで取る必要がある。

## 判断

- 宿の空きと料金は、楽天トラベルの空室検索 API（`https://openapi.rakuten.co.jp/engine/api/Travel/VacantHotelSearch/20170426`）から取る。緯度・経度と半径（0.1〜3.0km）、チェックインとチェックアウトの日、人数（大人・小学生の高学年と低学年・幼児の食事と布団の有無ごと）、部屋数で探せ、安い順に並べられる。日本の祭りの会場の近くを、人数と期間で探すという用途に合う
- 認証はアプリ ID（`applicationId`）とアクセスキー（`accessKey`）の両方が要る。アクセスキーはヘッダーで送り、URL に載せない。キーは環境変数（`RAKUTEN_APPLICATION_ID`・`RAKUTEN_ACCESS_KEY`）から読む。アプリの登録で求められる「許可されたWebサイト」は `RAKUTEN_ALLOWED_SITE` に入れ、サーバーからの呼び出しの `Referer` と `Origin` に付ける
- 呼び出しは、接客の旅程係の道具 `search_lodging` からだけ行う。宿の名前・料金・予約のページはツールの結果だけを使い、旅程の泊まり（`stay.lodging`）にはサーバーが付ける。旅程係が書いた宿の候補は使わない
- 料金の上限（`maxCharge`）は、1人あたりか1部屋あたりかが公式の説明に書かれていないので使わない。安い順に取り、予算の合計と上限を超えるかはコード（`apps/server/src/domain/lodging.ts`）で計算する
- 料金は、宿ごとにいちばん安いプランの1泊目の合計（`dailyCharge.total`）を使う。ないときは宿の最安値の目安（`hotelMinCharge`、1部屋1泊、税・サービス料込み）を使う。どちらも目安なので、調べた時刻と「料金と空きは、予約の時点で変わることがあります」を必ず添える
- 人数は1部屋で調べる。小学生は高学年、幼児は食事と布団なしとして渡す。内訳が細かく分からないので、料金を低く見積もらない側に寄せる
- キーがないときは、開発では架空の宿（名前に「（架空）」、URL は `example.com`）で動かし、本番では「調べられない」と返す。本番で架空の宿を出すと、本物と取り違えるため

公式のドキュメントで確かめたこと（2026-11-03）：

| 項目               | 確かめた内容                                                                                                                                                                       |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 入力               | 期間（`checkinDate`・`checkoutDate`）、人数（`adultNum` など、それぞれ0〜10）、位置（`latitude`・`longitude`、`datumType=1` で世界測地系の度）と半径（`searchRadius`、km）、並び順 |
| 出力               | 宿の番号・名前・宿の情報のページ・プランの一覧のページ・最安値の目安・緯度経度、プランごとの予約のページと1泊目の料金（`chargeFlag` で1人あたりか1部屋あたりかを示す）             |
| エラー             | 400 入力の誤り、404 データなし、429 呼び出しが多すぎる、500・503                                                                                                                   |
| 呼び出しの上限     | 数値は書かれていない。「短い時間の間に大量に、同一のリクエスト URL へアクセスすると、一定時間利用できなくなる場合がある」とだけある                                                |
| 出典の表示         | 楽天ウェブサービスを使うアプリは、バッジかテキスト「Supported by Rakuten Developers」（楽天ウェブサービスへのリンク）を表示する。提供された HTML をそのまま使う                    |
| 利用規約の主な制約 | 取得した情報を多くの人が共有できる場所に保存しない。決められた方法以外で複製・改変しない。収入は楽天アフィリエイト経由に限る。楽天グループとの提携を思わせる表示をしない           |

公式のドキュメントで確かめられなかったこと：

- 呼び出しの間隔の具体的な数値。ほかの開発者の報告では、間隔が1秒だと 429 になることがあるとされるので、1.5秒以上空ける。キーを登録したあと（人の作業）、実際の呼び出しで確かめる
- サーバーからの呼び出しで `Referer`・`Origin` が要るか。公式には、アプリの登録で「許可されたWebサイト」を入れることだけが書かれている。ヘッダーがなくて断られるという報告があるので、設定があれば付ける
- 返答の JSON の入れ子の正確な形。説明の表の分類だけで、見本の返答がない。読み取りは入れ子の形に頼らず、`hotelBasicInfo`・`roomBasicInfo`・`dailyCharge` を名前で探す

## 結果

- 良い点：宿の名前と料金に出典（予約サイトのページ）と調べた時刻が付き、モデルが作った宿の名前が旅程に入らない。予算を超えるかを、利用者に数字で示せる
- 引き受けること：
  - 取得した宿の情報は、その相談と、その相談の旅程の泊まりにだけ持つ。調べた結果は5分だけメモリで使い回し、ほかの相談の結果を出典なしで出さない
  - しおりや画面に宿の候補を出すときは、クレジット「Supported by Rakuten Developers」を表示し、調べた時刻と注意の一文を添える（画面の表示は別の変更で行う）
  - 利用規約にある、楽天市場へのリンクの求めと、共有のしおりに宿の情報を載せてよいかは、キーの登録のときに人が確かめる
  - アフィリエイト ID は使わない（このアプリは宿の紹介で収入を得ない）
