# ADR 0010：店と宿の一覧は OpenStreetMap で探し、公式のページで確かめる

- 状態：採用

## 背景

周辺係は Web 検索だけで店を探していて、見つからない会場では食事の予定が組めなかった。使う人には、昼ごはんの抜けた旅程が出ていた（計画の壁）。店と宿を場所から直接探せる情報源が要る。

条件は3つある。旅程の案の材料としてモデルに渡せること、旅程としおりに店の名前を保存できること、店の位置を画面の地図（Leaflet と OpenStreetMap のタイル）に出せること。

## 判断

1. **店と宿の一覧は、OpenStreetMap の一括データから祭りの周りだけを抜き出して持つ。** 周辺の店の種類と位置が、キーも費用もなしで分かり、保存もモデルへの受け渡しも地図への表示もできる。相談のたびの外への通信がないので、数ミリ秒で引けて、公開サーバーに負荷をかけない。抜き出したデータは `data/places/` に ODbL で公開する
2. **OpenStreetMap の店は「営業は要確認」として扱う。** 地図のデータでは臨時休業まで分からないので、`openStatus` はいつも `needs_check` にする。読める `opening_hours` は定休日と営業時間に使い、読めなければ分からないとする
3. **Web の調べに確かめる店として渡す。** 引いた店を周辺係の Web の調べに渡し、公式のページで営業を確かめてもらう。調べが失敗しても、引いた店で食事の候補を出す。同じ店は、営業まで確かめた Web の報告を残す
4. **宿は、空室検索 → Web の調べ → OpenStreetMap の順に使う。** OpenStreetMap の宿は空きも料金も分からないので、Web の調べと同じ注意を添える
5. **帰属を表示する。** 店と宿の出典は OpenStreetMap の元のページにし、題名を `© OpenStreetMap contributors` にする。画面の地図にも帰属を出している
6. **旅程に残すのは選んだ場所だけにする。** 旅程に残るのは、選んだ数か所の名前と位置と出典だけ。旅程は表示のための成果物で、元のデータベースの代わりにならない
7. **利用規約に触れるグルメの案内サイトは読まない。** 検索の言葉から案内サイトの名前を外し、WebFetch のフックでも止める（`isRestrictedSite`）。規約を読めなかったサイトも、安全のために同じに扱う
8. **Google マップへは、リンクだけで案内する。** 画面の旅程に、名前と位置から作った [Maps URLs](https://developers.google.com/maps/documentation/urls/get-started) を置く。Google のデータは取らず、キーも要らない

9. **複数の調べ方と出典を突き合わせて、提案の確かさを上げる。** 周辺の店は、観点（食べたいもの・食事に入れられる店・観光協会や商店街の案内・見つけた店の公式のページ）ごとに調べ役を並べて動かし、結果をコードで店ごとにまとめる（`mergeResearchedReports`）。別のサイトの出典が2つ以上ある店を corroborated にして上位に置く。営業は安全なほうに寄せ、読んだページに名前のない店は作り話として捨てる
10. **読むページの礼儀を守る。** 周辺の店と宿の調べでは、サイトの robots.txt が断るページを読まない（`agent/robots.ts`）。要約は自分の言葉で書き、口コミや点数を写さない

## 結果

- 1回の `search_nearby` で調べ役が最大4つ動くので、費用は1つのときの数倍になる（手元で試して約0.45ドル、約50秒）。同じ条件は6時間とっておく

- 店のある地域なら、Web の調べが失敗しても昼の候補が出る
- OpenStreetMap は登録の濃さに地域差があり、料理の種類や営業時間の登録は少ない。Web の調べで補う
- 祭りが増えたら、`data/places/` を作り直す。祭りが一覧にない会場では Web の調べだけで探す
- 手元のデータは一括データの時点のもので、閉店を反映しないことがある。営業を要確認として扱うのはそのため
