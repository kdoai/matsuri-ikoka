# コミット

## 決まり

- 形：`<種類>(<スコープ>): <要約>`。要約と本文は日本語でよい。要約は「何をしたか」を短く、末尾に句点を付けない
- 1コミット1目的。動く状態を保ったまま積む。目的の違う変更が混ざっていたら、コミットを分ける
- 作者は既定のまま（`git config user.name`・`user.email` を変えない。noreply のアドレスを使う設定になっている）
- `git add -A`・`git add .`・`git commit -a` は使わない。ファイルのパスを指定して足す
- `--no-verify` は使わない。フックに止められたら、書き方を直してからコミットし直す
- 秘密の値（鍵・トークン・`.env` の中身）や、個人を特定できる情報を入れない

| 種類       | 使いどころ             |
| ---------- | ---------------------- |
| `feat`     | 機能を足す             |
| `fix`      | 誤りを直す             |
| `docs`     | 文書だけを変える       |
| `test`     | テストだけを変える     |
| `refactor` | 動きを変えずに書き直す |
| `chore`    | 設定や依存の更新       |
| `ci`       | CI/CD の変更           |

| スコープ    | 場所                                                |
| ----------- | --------------------------------------------------- |
| `schema`    | `packages/schema`                                   |
| `server`    | `apps/server`（接客サーバー・接客エージェント）     |
| `agent-kit` | `packages/agent-kit`                                |
| `web`       | `apps/web`（画面）                                  |
| `3d`        | 3D の店とモデル（`assets/3d`、`apps/web/src/scenes`） |
| `shiori`    | 旅のしおり（HTML と PDF）                           |
| `data`      | `data/`（祭りのデータ・サンプルの相談）             |
| `infra`     | Dockerfile・デプロイ・GitHub の設定・`scripts/`     |
| `docs`      | `docs/`・README などの文書                          |

- スコープは Issue の `area:*` のラベルと同じ名前にしている
- 複数の場所にまたがるときは、いちばん主なものを1つ選ぶか、スコープを省く（例：`fix: …`）
- `ci` の種類にはスコープを付けなくてよい

## 手順

1. `git status` と `git diff`（足してあるものは `git diff --staged`）で、変更をすべて読む
2. 目的ごとに分ける。分けられないほど絡んでいれば、1つにまとめて本文で説明する
3. 変更に合わせて確かめる：`pnpm lint`・`pnpm typecheck`・`pnpm test`（スキーマやビルドに関わるなら `pnpm build`、画面なら e2e も）
4. パスを指定して足す：`git add path/to/a.ts path/to/b.ts`
5. `git diff --staged` を読み直し、意図しないファイル（`.env`、ビルドの成果物、`.blend`、手元のメモ）が入っていないことを確かめる
6. コミットする。本文は、なぜ変えたかを使う人にとっての理由で書く。最後に、会話の中で指示された署名の行（`Co-Authored-By: …`）を付ける

```bash
git commit -F - <<'EOF'
fix(server): 日帰りの移動の上限を超える祭りを候補から除く

移動が片道2時間を超える祭りが、日帰りの相談で候補に出ていた。
EOF
```

7. フックに止められたら、出力の理由を読み、該当する文やファイルを直して、新しくコミットし直す（`--amend` で前のコミットを書き換えない）

## 書いてはいけないこと

コミットの文・ブランチ名には、変更の中身と、使う人にとっての理由だけを書く。実在の祭りでの相談の例は書かない。テストやサンプルに出す祭りは架空のものにする。
